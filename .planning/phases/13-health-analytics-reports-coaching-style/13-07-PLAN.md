Build `app/analytics/reports.py` — one composer, two windows (D-04).

Purpose: RPT-01 and RPT-02 ask for a weekly and a monthly report covering training volume,
strength progression, weight and measurement changes, nutrition, trends and program context.
D-04 fixes the shape: ONE composer function with a period parameter, same sections in both, not
two composers. ARCHITECTURE.md Anti-Pattern #9 and D-02/D-03 fix the discipline: this module
COMPOSES and never computes — "a report with its own volume sum is how the report and the
summary disagree about the same week." `recomposition.py` is the precedent, and its own module
docstring states the rule: "Composition only -- no SQL of its own beyond the envelope."

Two ambiguities RESEARCH left open are resolved here, deliberately and in writing:

**Closed-period reading.** D-01 says "Monday–Sunday for the weekly report, calendar month for
the monthly one." 13-RESEARCH.md's Assumption A1 flagged that ARCHITECTURE.md's older phrasing
("the completed week") and D-04's phrasing ("the current week") read differently. **Decision:
the CURRENT period through today** — Monday-of-this-week to today, and first-of-this-month to
today. D-04's literal text says "the current week" and "the current calendar month"; every other
anchored tool in this codebase ends on today; and a report a user asks for on Wednesday should
describe the week they are in, not the one that ended three days ago. The anchor is still a
calendar boundary, which is what "closed-period" means as against a rolling trailing-N-days
window.

**Window derivation.** RESEARCH recommended reusing `_common.window_from_weeks(weeks=1)`.
`analytics/` cannot import `app.mcp` (`test_analytics_isolation.py`), so this module uses
`core/time.py::local_week_start` instead — which computes the identical Monday
(`day - timedelta(days=day.weekday())`) and lives in the module whose docstring says every
day/week grouping routes through it. A test asserts the two agree, so they cannot drift.

Output: `ReportPeriod`, `ReportResult`, and `compose_report`.

**Window resolution** — a small pure-ish helper so the two periods differ in exactly one line:

    async def resolve_report_window(
        session: AsyncSession, *, user_id: uuid.UUID, period: ReportPeriod
    ) -> tuple[dt.date, dt.date, str]:
        """The report's closed period, plus the timezone it was computed in.

        Uses the same probe idiom every anchored analytics function uses: ``resolve_window`` is
        the only sanctioned reader of ``users.timezone``, but the anchor day cannot be known
        until the timezone is, so a throwaway one-day window is resolved purely to obtain ``tz``.
        """
        probe_day = local_day(utc_now(), "UTC")
        tz = (await resolve_window(session, user_id=user_id, start_day=probe_day,
                                   end_day=probe_day, snap_to_weeks=False)).tz
        now = utc_now()
        end_day = local_day(now, tz)
        if period is ReportPeriod.WEEKLY:
            start_day = local_week_start(now, tz)
        else:
            start_day = local_month_start(now, tz)
        return start_day, end_day, tz
