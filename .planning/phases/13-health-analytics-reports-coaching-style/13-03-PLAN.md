<objective>
Build the three pieces `analytics/reports.py` needs before it can exist: a calendar-month
boundary helper, the five-resource freshness bundle, and — the real work — a cross-exercise
personal-record scan.

Purpose: 13-RESEARCH.md's single most important non-obvious finding is that
`get_personal_records` takes a **mandatory** `exercise_template_external_id` and has no
cross-exercise mode, so D-02's "PR highlights" cannot be built by calling it in a loop without
reproducing exactly the query fan-out PITFALLS #18 warns against on a `MIN_INSTANCES=0`
service. RESEARCH offered two options and left the decision to planning.

**Decision: Option 1 — build the purpose-built cross-exercise scan, homed in
`analytics/records.py`.** Option 2 (approximating PRs from `get_plateaus`'
`historical_best_kg`/`recent_performance_kg`) was rejected because it silently narrows "personal
record" to an e1RM/weight signal, dropping `MAX_REPS` and `SESSION_VOLUME` — two of the four
`PersonalRecordType` members — and would make the report's "PR highlights" mean something
different from what `fitness_get_personal_records` means by the same word. Option 1 is not
expensive: `rollup.qualifying_set_rows` already accepts `template_external_ids=None` and returns
every non-warm-up set in a window at set grain in ONE query (measured 889 rows in 10.07 ms for a
12-week window; 7,719 rows in 17 ms all-time), and `QualifyingSetRow` already carries
`template_external_id` and `title`. The scan is one query and a Python fold — the same shape
`get_plateaus` already uses to avoid the per-exercise loop.

Output: `local_month_start`, `FRESHNESS_RESOURCES_REPORT`, `get_recent_records`, and their tests.
</objective>

```python
def local_month_start(ts: dt.datetime, tz: str) -> dt.date:
    """First calendar day of the user's local month -- matches ``date_trunc('month', ...)``.

    The month sibling of ``local_week_start``, and it lives here for the reason this module's
    docstring gives: every day/week grouping in this project routes through here. RPT-02's
    calendar-month report window is the first month-grained question the project has asked, and
    an ad-hoc ``day.replace(day=1)`` inside ``analytics/reports.py`` would be the second place
    the timezone rule is applied and the first place it could be applied wrongly.

    At UTC+7, 18:00Z on the last day of a month is already 01:00 on the FIRST of the next one.
    Deriving the month from the server's UTC date instead would report the previous month for
    seven hours out of every twenty-four -- silently, as a report that is one month stale.
    """
    day = local_day(ts, tz)
    return day.replace(day=1)
```

```python
class RecentRecord(_AnalyticsModel):
    """One personal record that was SET inside a window, with the exercise that set it.

    Deliberately NOT ``PersonalRecordsResult`` narrowed. That model answers "what are this
    exercise's best-ever numbers", is scoped to ONE exercise by a mandatory
    ``exercise_template_external_id``, and its ``records`` are the best values found INSIDE the
    window whether or not they beat anything. This model answers a different question -- "what
    got beaten this week, across everything I trained" -- and a value that merely led its own
    window is not a record. Reporting one as the other is the plausible-looking-but-quietly-wrong
    failure this project treats as its primary risk.

    ``previous_value`` is the incumbent this record beat, computed from all history strictly
    BEFORE ``window_start``. ``None`` means there was no incumbent -- the first time this
    exercise produced an eligible set of this type -- which is a real and different fact from
    "beat a small number", and collapsing the two would let a first-ever log read as a
    breakthrough.
    """

    exercise_template_external_id: str
    title: str | None
    record: PersonalRecord
    previous_value: Decimal | None


class RecentRecordsResult(_AnalyticsModel):
    """PROG-04 asked cross-exercise, for D-02's report "PR highlights".

    ``records`` is sorted ``achieved_on`` DESCENDING, then ``record.record_type.value``, then
    ``exercise_template_external_id`` -- newest first, because the consumer TRUNCATES this list
    to a small cap and the most recent record is the one a weekly report is about. The two
    secondary keys exist so the truncation point is deterministic rather than planner-dependent,

    matter more here than usual, because the report that embeds this carries a
    ``get_recomposition_status`` verdict anchored on a DIFFERENT window (D-01).
    """
```

**Algorithm** (one query, one pass, no second aggregate):

1. Resolve the window WITHOUT week snapping — `resolve_window(..., snap_to_weeks=False)`. A
   record is a point in time and has no bucket to be comparable with; `get_personal_records`
   already says exactly this.
2. Seed from history, mirroring `get_plateaus`:
   ```python
   earliest = await earliest_workout_at(session, user_id=user_id)
   history_start = start_day if earliest is None else local_day(earliest, window.tz)
   clamp_floor = end_day - dt.timedelta(days=MAX_ANALYTICS_WINDOW_DAYS - 1)
   history_start = max(min(history_start, start_day), clamp_floor)
   ```
   Then build a SECOND window over `[history_start, end_day]` (again `snap_to_weeks=False`) and
   issue ONE `qualifying_set_rows(session, user_id=user_id, window=history_window,
   template_external_ids=None)`. Split in Python on `row.local_day < start_day`, exactly as
   `get_plateaus` splits its seeded history — not two queries.
3. Per `template_external_id`, maintain two parallel accumulator sets: `prior` (rows strictly
   before `start_day`) and `current` (rows in `[start_day, end_day]`), each holding the best
   `_RecordKey` for `MAX_WEIGHT`, `MAX_REPS` and `ESTIMATED_1RM`, plus a per-`workout_id`
   `_SessionVolume` map for `SESSION_VOLUME`.
   * Reuse `_key` and `_better` for every comparison — do NOT write a second tie-break rule.
   * Reuse `estimate_1rm(weight_kg=..., reps=..., exercise_type=...)` for the e1RM candidate; a
     `None` is an ineligible ESTIMATE, never an ineligible set.
   * `MAX_REPS` is deliberately un-gated by the 12-rep estimate cap — the rep PR is precisely
     the record that lives above that range.
   * Session volume accumulates only when BOTH `weight_kg` and `reps` are present (operand
     presence, never a modality allow-list), quantized with `_VOLUME_QUANTUM` at the end.
4. Emit a `RecentRecord` for each `(template, record_type)` where the current-window best exists
   AND `_better(current_key, prior_key)` is True. `previous_value` is `prior_key[0]` when a
   prior key exists, else `None`.
5. `title` comes off the `QualifyingSetRow` that produced the record — `QualifyingSetRow.title`
   is carried for exactly this reason ("PROG-01..PROG-04 and CMP-01 all want an exercise title
   and selecting it in this join costs nothing"). Do not issue a template lookup.
6. Sort `records` by `(-achieved_on.toordinal(), record.record_type.value,
   exercise_template_external_id)` — newest first, deterministic tie-break.
7. `coverage = await build_coverage(session, user_id=user_id, utc_start=window.utc_start,
   utc_end=window.utc_end)` over the REQUESTED window (not the seeded history window) — the
   coverage envelope describes the window the caller asked about.
   `freshness = await build_freshness(session, user_id=user_id,
   resources=FRESHNESS_RESOURCES_MUSCLE)` — the same bundle `get_personal_records` uses, and for
   its reason: `exercise_type` gates e1RM eligibility and comes from the templates, so a stale
   template sync silently changes which records exist.

**Do not** add a row cap. The consumer (`analytics/reports.py`, plan 13-07) truncates with
`_common.truncate()`; a silent truncation inside the analytics layer would be a wrong answer,
which is the rule `records.py`'s docstring already states about `reps_at_weight`.
