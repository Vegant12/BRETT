```python
def _degraded_comparison() -> PeriodComparisonResponse:
    return PeriodComparisonResponse(
        data_available=False, period_a=None, period_b=None, totals=[],
        exercises=[], exercises_truncated=False, total_exercises=0,

    )


@safe_tool(degraded=_degraded_comparison)
async def fitness_compare_periods(
    ctx: Context[AppContext],
    period_a_start: Annotated[dt.date, Field(description="Baseline period start (inclusive).")],
    period_a_end: Annotated[dt.date, Field(description="Baseline period end (inclusive).")],
    period_b_start: Annotated[dt.date, Field(description="Comparison period start (inclusive).")],
    period_b_end: Annotated[dt.date, Field(description="Comparison period end (inclusive).")],
    include_muscle_groups: Annotated[
        bool, Field(description="Also break the comparison down by muscle group.")
    ] = False,
) -> PeriodComparisonResponse:
    """Compare two date periods, with every figure normalized per week so unequal-length windows
    do not produce misleading deltas.

    Period A is the BASELINE and period B the comparison: every delta reads "B minus A", so a
    positive number means more recently. To compare "the last 4 weeks against the previous 4",
    pass the OLDER range as A.
    """
```
Body:
1. `user_id = resolve_user_id(ctx)`.
2. Validate both periods in-body, BEFORE opening a session, and return a degraded-but-successful
   response rather than raising:
   - `end < start` for either period, or
   - `(end - start).days + 1 > MAX_COMPARISON_PERIOD_DAYS` (365) for either period.
   On failure return `_degraded_comparison()` and `log.warning("mcp_compare_periods_invalid_range")`
   with NO date values in the event. Comment: a raise here would reach Claude verbatim (Pitfall 3),
   and the four dates are the model's own arguments so echoing them adds nothing; a
   `data_available=False` response is a correct, schema-valid "I could not do that". Dates cannot
   carry a `Field(le=...)` bound the way integers can, so this is the one place a tool validates
   its own arguments.
3. Open `read_only_session`; call `compare_periods(session, user_id=user_id, period_a_start=...,
   period_a_end=..., period_b_start=..., period_b_end=...,
   include_muscle_groups=include_muscle_groups)`.
4. Truncate both per-exercise lists to `MAX_COMPARISON_ITEMS` (25), each sorted by
   `(-abs(delta or 0), exercise_template_external_id or "")` so the BIGGEST movements survive the
   cap -- a comparison truncated to the alphabetically-first 25 exercises is worse than useless.
   Use `truncate()` for both, so each gets its `*_truncated` + `total_*` pair.
   `totals` and `muscle_groups` pass through untruncated: `totals` is a handful of metric rows and
   `muscle_groups` is bounded at 19 by the taxonomy.
5. Return with `data_available=True` and every field mapped through.

```python
def _degraded_trend() -> BodyWeightTrendResponse:
    return BodyWeightTrendResponse(data_available=False, trend=None)


@safe_tool(degraded=_degraded_trend)
async def fitness_get_body_weight_trend(ctx: Context[AppContext]) -> BodyWeightTrendResponse:
    """Body-weight trend anchored on today: 7-, 14- and 30-day rolling averages, the smoothed
    four-week rate of change in kg and percent per week, and the coverage behind each figure.
    """
    user_id = resolve_user_id(ctx)
    async with read_only_session(ctx) as session:
        trend = await get_body_weight_trend(session, user_id=user_id)
    return BodyWeightTrendResponse(data_available=True, trend=trend)


def _degraded_recomposition() -> RecompositionResponse:
    return RecompositionResponse(data_available=False, recomposition=None)


@safe_tool(degraded=_degraded_recomposition)
async def fitness_get_recomposition_status(ctx: Context[AppContext]) -> RecompositionResponse:
    """Where body recomposition stands right now: a status verdict derived from the body-weight
    trend and the aggregate training-progression signal, with the disclaimer that frames it as
    decision support rather than a medical claim.
    """
    user_id = resolve_user_id(ctx)
    async with read_only_session(ctx) as session:
        recomposition = await get_recomposition_status(session, user_id=user_id)
    return RecompositionResponse(data_available=True, recomposition=recomposition)
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Claude → four `dt.date` arguments | The only tool arguments in the phase that cannot carry a numeric `Field` bound |
| Tool → read-only session → analytics | `get_recomposition_status` fans out to several aggregate queries inside one transaction |
| Tool exception → Claude | `safe_tool` is the only guard on this channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-05 | Denial of Service | an unbounded period (e.g. year 1000 to 3000) or a 40-exercise comparison with muscle groups (31 KB structured / 73 KB wire) | mitigate | In-body validation rejects reversed periods and anything over `MAX_COMPARISON_PERIOD_DAYS` (365) before a session is opened; `MAX_COMPARISON_ITEMS` (25) caps both per-exercise lists; `include_muscle_groups` defaults to `False`. Budget 32 KB enforced in plan 06-10 |
| T-06-01 | Information Disclosure | a raise from the date validation, or an asyncpg error carrying the DSN | mitigate | Validation returns a degraded response instead of raising; `log.warning("mcp_compare_periods_invalid_range")` carries no date values; `@safe_tool` catches everything else |
| T-06-02 | Elevation of Privilege | `user_id` as a tool parameter | mitigate | `resolve_user_id(ctx)` server-side in all three tools; no parameter named `user_id` |
| T-06-03 | Tampering | a write reaching the database | mitigate | `read_only_session` (`postgresql_readonly=True`); no write construct imported |
| T-06-06 | Tampering (integrity) | `include_muscle_groups=True` bypassing the muscle-mapping override | mitigate | The flag is passed through to `compare_periods`, which resolves muscles via `effective_muscles_bulk`; this module never touches `exercise_muscles` |
| T-06-09 | Repudiation / integrity of advice | dropping `RecompositionResult.disclaimer`, turning decision support into an unqualified body-composition claim | mitigate | `RecompositionResponse` embeds `RecompositionResult` whole rather than projecting fields, so the disclaimer cannot be omitted by construction |
| T-06-11 | Tampering (integrity) | a truncated comparison list read as complete | mitigate | `exercises_truncated`/`total_exercises` and `exercise_levels_truncated`/`total_exercise_levels` are required response fields; the cap keeps the largest movements, not the alphabetically first |
| T-06-13 | Denial of Service (latency) | `fitness_get_recomposition_status` running several aggregates in one call against Claude's 10 s discovery / 30 s call budget | accept | Single user, ~8k sets; Phase 4 measured the underlying aggregate at ~50 ms. Recorded here and re-checked against the live dataset at the Phase 6 smoke test rather than pre-optimized |
