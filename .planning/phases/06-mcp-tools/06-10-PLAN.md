Measurement rule, verified against the installed `mcp 2.0.0` — measure the WHOLE result:
```python
size = len(result.model_dump_json(exclude_none=True).encode("utf-8"))
```
`FuncMetadata.convert_result` builds `unstructured_content = pydantic_core.to_json(result,
fallback=str, indent=2)` — pretty-printed — AND sets `structured_content`. Both travel to the
client. Measured on a 52-week `WeeklyVolumeResult`: 5,211 bytes structured, 7,819 bytes text,
**14,304 bytes total**. A budget written against `structured_content` alone understates Claude's
real context cost by ~2.7x. There is no supported way to suppress the text block while keeping
`outputSchema`.

From `backend/tests/conftest.py` (plan 06-03): `committed_history` (a `GoldenBuilder` with a
purge-and-commit teardown; the test commits) and `worst_case_history` (52 weeks x 5 sessions/week x
30 templates, plus ~120 daily body measurements and sync-state rows, all committed, anchored on
`utc_now()`).

From `backend/tests/test_mcp_tools.py`: the in-memory client pattern —
```python
from mcp import Client
```

imported INSIDE the test function (Pitfall 8), with the `client: TestClient` fixture taken even

Create `backend/tests/test_mcp_readonly.py`. Every test `@pytest.mark.integration` — these need a
real PostgreSQL, which is the whole point: an annotation is a hint and only the server can refuse.

Module docstring: MCP-05's runtime half. `ToolAnnotations(read_only_hint=True)` is documented by
the SDK as a hint that "should not be relied upon for security enforcement";
`postgresql_readonly=True` makes asyncpg open the transaction with `READ ONLY` so the SERVER
raises. Also record the two findings that contradict what the docs would lead you to expect:
it works at the DEFAULT isolation level (SQLAlchemy's PG docs claim asyncpg needs SERIALIZABLE —
adding it would buy serialization-failure retries for no benefit), and the flag does not leak back
into the pooled connection.

Build a minimal fake context rather than going through `Client(mcp)`, so the test targets
`read_only_session` directly:

```python
@dataclass
class _FakeRequestContext:
    lifespan_context: AppContext


@dataclass
class _FakeCtx:
    request_context: _FakeRequestContext
```
Construct it from `client.app.state.sessionmaker` (the `client` fixture is still required, per
Pitfall 7).

Tests:

1. `test_the_transaction_is_actually_read_only` — inside `async with read_only_session(ctx) as
   session:` assert `await session.scalar(text("SHOW transaction_read_only")) == "on"`. (Raw
   `text()` is fine here — `test_mcp_isolation.py` walks `app/mcp/`, not `backend/tests/`.)
2. `test_an_insert_is_refused_by_the_server` — inside the same context manager, attempt an INSERT
   into `workouts` and assert it raises. Assert on the DBAPI error class name containing
   `ReadOnlySQLTransaction` rather than importing `asyncpg.exceptions` directly, so the assertion
   survives a driver swap; use `pytest.raises(Exception)` and inspect
   `type(excinfo.value.orig).__name__` if the error is wrapped by SQLAlchemy. Message names MCP-05
   and Phase 6 success criterion #4.
3. `test_an_update_and_a_delete_are_refused_too` — same shape for an `UPDATE users SET timezone`
   and a `DELETE FROM sync_state`, so the guarantee is not accidentally INSERT-only.
4. `test_the_readonly_flag_does_not_leak_into_the_pool` — after the `read_only_session` block
   exits, open a PLAIN session on the same engine, assert `SHOW transaction_read_only` is `off`,
   perform a real write (insert then delete a `sync_state` row), and commit. Docstring: if the flag
   leaked back, the Hevy sync CLI and `/health` would start failing at random after any MCP call,

5. `test_the_session_is_rolled_back_on_exit` — enter the context manager, run a `SELECT`, exit
   normally, and assert `session.in_transaction()` is `False`. Docstring: analytics never writes so

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Tool response → Claude's context window | Every byte returned is a byte consumed; MCP-03 is a resource-exhaustion control, not a style preference |
| Tool session → PostgreSQL write path | The `READ ONLY` transaction is the only thing standing between a future bug and this project's only copy of 17 months of training history |
| MCP connection pool → the Hevy sync CLI and `/health` | A leaked `readonly` characteristic would break the write path from a distance |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-05 | Denial of Service | any tool returning an unbounded payload (measured worst case: 348 KB wire for a 52-week muscle grid) | mitigate | `BUDGETS` covers all thirteen tools, asserted equal to the live registry; every tool measured at its PUBLISHED CAP, not its default, on the full `CallToolResult` |
| T-06-05 | Denial of Service | a regression reverting the muscle rollup to the per-week grid | mitigate | `test_muscle_group_volume_is_flat_across_windows` fails loudly at a 4-vs-52-week size divergence, in the same terms the decision was made in |
| T-06-03 | Tampering | any write reaching PostgreSQL from the MCP surface | mitigate | `test_an_insert_is_refused_by_the_server` and `test_an_update_and_a_delete_are_refused_too` prove the SERVER raises, not the application; `test_a_tool_call_leaves_no_rows_behind` proves it end-to-end through a composed tool |
| T-06-17 | Denial of Service (collateral) | the `readonly` transaction characteristic leaking back into the pooled connection and breaking the Hevy sync CLI | mitigate | `test_the_readonly_flag_does_not_leak_into_the_pool` performs a real write on a later plain session from the same engine |
| T-06-11 | Tampering (integrity) | a truncated list read as complete | mitigate | `test_truncated_lists_declare_themselves` asserts `total_exercises` reflects reality and `exercises_truncated` is consistent with the returned length |
| T-06-18 | Denial of Service (test integrity) | budget tests passing because the fixture seeded nothing | mitigate | `test_every_tool_response_fits_its_budget` also asserts `result.is_error is False` for every tool, and `test_weekly_volume_returns_exactly_the_requested_week_count` fails on an empty database |
</threat_model>
