**Module docstring** must name `MCP-02, MCP-03, MCP-06` and `D-02, D-09, D-11, D-13`, and state
the three load-bearing design rules with their measured consequence:

1. Every model here **composes** an `app/analytics/schemas.py` result as a field; it never restates
   its arithmetic. The one deliberate reshape in this phase is
   `MuscleGroupVolumeResponse` (see task 2) and it is documented at that model.
2. Every response carries `data_available: bool`. `False` means the tool could not reach its data
   (see `_common.safe_tool`); it is NOT the same claim as "you trained zero sets", and without this
   field a degraded payload is indistinguishable from a real empty result -- a wrong answer with no
   signal.
3. Never a union RETURN annotation. `mcp 2.0.0` sets `wrap_output=True` for unions, scalars, lists
   and tuples, which changes `structured_content` from `{...}` to `{"result": {...}}` on **every**
   call including successes. A single `BaseModel` return with an optional payload field is
   unwrapped. (An optional FIELD is fine; only the return annotation matters.)

**Base model** — mirror `_AnalyticsModel` exactly, with its own docstring restating why each of
the three settings is set here too:

class MuscleGroupRollup(_McpModel):
    """One muscle group's whole-window totals. THE ONE DELIBERATE RESHAPE IN THIS PHASE.

    CONTEXT.md's rule is "compose these, do not reshape them". This model breaks it exactly once,
    on purpose, for a measured reason: `MuscleGroupVolumeResult`'s shape is weeks x 19 muscle
    groups, so D-04's 52-week cap bounds it at 988 rows -- 128,290 bytes of structured JSON and
    ~347,707 bytes on the wire. Rolled up over the window it is 19 rows and ~7,851 bytes at ANY
    window. The per-week TOTAL trend is still available from `fitness_get_weekly_volume`, and
    muscle-level period-over-period movement from `fitness_compare_periods`; what is given up is
    the per-week x per-muscle grid, which is not what "which muscles are undertrained?" asks.

    `direct_sets`/`indirect_sets`/`weighted_sets` are SUMS over the window's weeks -- set counts
    are additive. `sessions`/`sessions_per_week` are NOT: they come from `get_training_frequency`,
    which de-duplicates workouts across the whole window. Summing per-week session counts inflated
    14 of 16 muscle groups by up to 4.0x on real data (`analytics/frequency.py` module docstring).
    """
    muscle_group: CanonicalMuscleGroup
    direct_sets: int
    indirect_sets: int
    weighted_sets: Decimal
    sessions: int
    sessions_per_week: Decimal
    insufficient_data: bool


class MuscleGroupVolumeResponse(_McpModel):
    """VOL-02 for MCP. `muscles` ALWAYS has 19 rows, one per canonical muscle group, sorted by
    `muscle_group.value` -- an untrained group is a zero row, never an absence. A zero row is the
    most diagnostically interesting one for "which muscles are undertrained?", which is exactly
    why it must not be omitted."""
    data_available: bool
    window_start: dt.date | None
    window_end: dt.date | None
    weeks: int | None
    muscles: list[MuscleGroupRollup]
    coverage: CoverageMetadata | None
    freshness: FreshnessMetadata | None
