```python
def _degraded_recent() -> RecentWorkoutsResponse:
    return RecentWorkoutsResponse(
        data_available=False, limit=0, workouts=[], freshness=None
    )


@safe_tool(degraded=_degraded_recent)
async def fitness_get_recent_workouts(
    ctx: Context[AppContext],
    limit: Annotated[
        int,
        Field(
            ge=1,
            le=MAX_RECENT_WORKOUTS,
            description="How many recent workouts to list, newest first. Max 25.",
        ),
    ] = 10,
) -> RecentWorkoutsResponse:
    """The most recent workouts as compact summaries: date, title, duration, exercise count,
    hard sets and tonnage. No per-exercise or per-set detail -- call `fitness_get_workout` with a
    `workout_id` from this list for that.
    """
    user_id = resolve_user_id(ctx)
    async with read_only_session(ctx) as session:
        tz = await local_timezone(session, user_id=user_id)
        rows = await recent_workout_summaries(session, user_id=user_id, tz=tz, limit=limit)
        freshness = await build_freshness(
            session, user_id=user_id, resources=FRESHNESS_RESOURCES_WORKOUTS
        )
    return RecentWorkoutsResponse(
        data_available=True,
        limit=limit,
        workouts=[WorkoutSummary(...) for row in rows],   # field-for-field from WorkoutSummaryRow
        freshness=freshness,
    )
```

Notes the executor must honour:
- `limit`'s `Field(ge=1, le=MAX_RECENT_WORKOUTS)` lands `{"minimum": 1, "maximum": 25,
  "default": 10}` in `inputSchema` AND is enforced by the SDK before the body runs. Keep the
  constraint rather than validating in-body: advertising the bound prevents far more bad calls than
  a prettier error message fixes.
- Count-based, never days-based (D-10): a days-based window lets a high-frequency training period
  return an unpredictably large list, which is exactly what MCP-03 forbids.
- `user_id` is never a parameter and must not appear in `inputSchema` (ASVS V4 / IDOR).
- Everything that touches the session happens inside the `async with`; build the response after it
  closes only if every value has already been read.

```python
def _degraded_workout() -> WorkoutDetailResponse:
    return WorkoutDetailResponse(
        data_available=False,
        requested_workout_id="",
        found=False,
        workout=None,
        freshness=None,
    )


@safe_tool(degraded=_degraded_workout)
async def fitness_get_workout(
    ctx: Context[AppContext],
    workout_id: Annotated[
        str,
        Field(
            min_length=1,
            max_length=64,
            description="The workout id echoed by fitness_get_recent_workouts.",
        ),
    ],
) -> WorkoutDetailResponse:
    """The full exercise and set breakdown for exactly one workout, identified by the
    `workout_id` that `fitness_get_recent_workouts` returns for it. Includes warm-up sets, each
    labelled by `set_type`.
    """
```
Body: resolve `user_id`, open `read_only_session`, read `tz`, call
`workout_detail(session, user_id=user_id, external_id=workout_id, max_sets=MAX_WORKOUT_SETS)`,
build `freshness` from `FRESHNESS_RESOURCES_WORKOUTS`. If the repository returned `None`, return
`WorkoutDetailResponse(data_available=True, requested_workout_id=workout_id, found=False,
workout=None, freshness=freshness)` — a missing workout is an ordinary successful answer, not an
error and not a `data_available=False`. Otherwise map the nested dataclasses field-for-field into
`WorkoutDetail` / `WorkoutExerciseDetail` / `WorkoutSetDetail`, setting
`sets_truncated=row.total_sets > MAX_WORKOUT_SETS`.

Notes the executor must honour:
- `max_length=64` matches `workouts.external_id`'s `String(64)`: an over-long id is rejected by the
  SDK before any query runs, which is the cheapest possible ASVS V5 control here.
- D-12: keyed on the Hevy external id, never a calendar date and never the internal
  `workouts.id` UUID. A date-keyed lookup would need a same-day-multiple-workouts policy that an
  id-keyed one avoids entirely.
- The distinction between `found=False` (no such workout) and `data_available=False` (the tool
  could not reach the data) must be stated in a comment — conflating them is how "you have no
  workout on record" gets said about a database outage.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Claude → `limit` / `workout_id` arguments | Untrusted model-chosen scalars |
| Tool → read-only session → PostgreSQL | Every query here runs inside a `READ ONLY` transaction |
| Tool exception → Claude | `mcp 2.0.0` returns `str(e)` verbatim; `safe_tool` is the only thing standing in the way |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Information Disclosure | either tool body raising (asyncpg connection errors carry the full DSN) | mitigate | `@safe_tool(degraded=...)` on both; detail to `log.exception("mcp_tool_failed")`, caller gets `data_available=False`. No `str(e)` anywhere in the module |
| T-06-02 | Elevation of Privilege | reading another user's workout by guessing a `workout_id` | mitigate | `resolve_user_id(ctx)` server-side; `user_id` is not a tool parameter; the repository filters on it. Proven by `test_another_users_workout_is_never_returned` (plan 06-03) |
| T-06-03 | Tampering | a write reaching the database from a tool | mitigate | `read_only_session` sets `postgresql_readonly=True`; no write construct imported in this module |
| T-06-04 | Tampering | injection via `workout_id` | mitigate | Bound parameter in the repository; `Field(max_length=64)` rejects over-long input before any query; no `text(` in this module |
| T-06-05 | Denial of Service | an unbounded workout list or an enormous single workout | mitigate | `Field(le=MAX_RECENT_WORKOUTS)` published as `"maximum": 25`; `max_sets=MAX_WORKOUT_SETS` (120) with `total_sets` reporting the truth. Budgets 20 KB / 32 KB enforced in plan 06-10 |
| T-06-08 | Information Disclosure (low) | SDK validation error echoing a rejected `limit` or `workout_id` | accept | The echoed value is the model's own argument, never server state. Both parameters are scalars, never a pass-through object |
</threat_model>
