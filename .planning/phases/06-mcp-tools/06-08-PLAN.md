Create `backend/app/mcp/tools/summary.py`. Module docstring names `MCP-02, MCP-03, MCP-05, MCP-06`
and `D-08`, and records the two facts a reader needs:
1. What is deliberately EXCLUDED and why: personal records and plateaus keep their own dedicated
   tools rather than duplicating data into the tool every conversation opens with; the per-week x
   per-muscle grid and the per-exercise frequency list are dropped for size (composing the four
   results verbatim is ~24 KB structured / ~57 KB wire at 4 weeks; this shape is ~3,963 / ~9,502).
2. The cost: this tool issues four analytics calls, and `get_recomposition_status` alone runs
   `get_body_weight_trend` + `get_exercise_trends` + `get_weekly_volume` over 12 weeks -- roughly
   seven aggregate queries in one tool call. All inside ONE read-only transaction, which is
   correct: one consistent snapshot. Claude's connector timeouts are 10 s for discovery and a slow
   first tool call is the worst first impression this project can make, so if this ever needs
   optimizing, that is where to look.

```python
def _degraded_summary() -> TrainingSummaryResponse:
    return TrainingSummaryResponse(
        data_available=False, window_start=None, window_end=None, weeks=None,
        sessions_per_week=None, volume_by_week=[], muscles=[],
        recomposition_status=None, recomposition_disclaimer=None,
        progression_signal=None, progression_verdict=None,
        weight_trend_rate_percent_per_week=None, average_7d_kg=None,
        coverage=None, freshness=None,
    )


@safe_tool(degraded=_degraded_summary)
async def fitness_get_training_summary(
    ctx: Context[AppContext],
    weeks: Annotated[
        int,
        Field(
            ge=1,
            le=MAX_SUMMARY_WEEKS,
            description="Whole weeks back from today, ending today. Max 12.",
        ),
    ] = 4,
) -> TrainingSummaryResponse:
    """The composed picture of training state in one call: weekly volume, how much work each of
    the 19 muscle groups is getting and how often, the aggregate progression verdict, and the
    current recomposition status with its disclaimer.

    Personal records and plateaus are deliberately not included -- ask `fitness_get_personal_records`
    or `fitness_get_plateaus` for those.
    """
```
Body, all inside one `async with read_only_session(ctx) as session:`:
1. `start_day, end_day = await window_from_weeks(session, user_id=user_id, weeks=weeks)`
2. `weekly = await get_weekly_volume(session, user_id=user_id, start_day=start_day, end_day=end_day)`
3. `muscle_volume = await get_muscle_group_volume(session, user_id=user_id, start_day=start_day,
   end_day=end_day)`
4. `frequency = await get_training_frequency(session, user_id=user_id, start_day=start_day,
   end_day=end_day)`
5. `recomposition = await get_recomposition_status(session, user_id=user_id)`

Then build the response:
- `volume_by_week=[SummaryVolumeWeek(week_start=w.week_start, sessions=w.sessions,
  hard_sets=w.hard_sets, total_reps=w.total_reps, tonnage_kg=w.tonnage_kg)
  for w in weekly.weeks]` — `tonnage_sets` is dropped here on purpose (it is the operand-presence
  denominator, useful when auditing a number but not when summarizing); note that in a comment.
- `muscles=roll_up_muscles(muscle_volume, frequency)` — the SAME fold
  `fitness_get_muscle_group_volume` uses, imported rather than re-derived, so the two tools can
  never disagree about a muscle's set count.
- `sessions_per_week=frequency.sessions_per_week`
- `recomposition_status=recomposition.status`
- `recomposition_disclaimer=recomposition.disclaimer` — VERBATIM, never reworded, never truncated.
  Comment it: `analytics/schemas.py` calls this "a REQUIRED FIELD, not documentation" precisely so
  a Phase 6 serialization change cannot drop it, and dropping it here is exactly the failure that
  docstring anticipates.
- `progression_signal=recomposition.progression_signal.signal`,
  `progression_verdict=recomposition.progression_signal.verdict`
- `weight_trend_rate_percent_per_week=recomposition.weight_trend.trend_rate_percent_per_week`,
  `average_7d_kg=recomposition.weight_trend.average_7d_kg`
- `coverage=weekly.coverage`, `freshness=muscle_volume.freshness` — freshness from the MUSCLE
  result because it covers BOTH `workouts` and `exercise_templates`; the summary reports per-muscle
  numbers, so a stale template sync silently changes them and the weekly-volume freshness
  (workouts only) would claim a freshness this response does not have. Comment it.
- `window_start=start_day`, `window_end=end_day`, `weeks=weeks`, `data_available=True`.

`MAX_SUMMARY_WEEKS` is 12 and the default is 4 (D-08 leaves the default to discretion; 4 weeks is
one training block, and it measures ~9.5 KB wire against a 16 KB budget while 12 weeks measures
~11.5 KB). State that reasoning in a comment beside the `Field`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Claude → `weeks` argument | Bounded at 12 by the published schema — tighter than every other window tool |
| Tool → one read-only transaction → seven aggregate queries | The heaviest single tool call in the phase |
| Tool exception → Claude | `safe_tool` is the only guard on this channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-05 | Denial of Service | composing four analytics results verbatim (~24 KB structured / ~57 KB wire at 4 weeks) in the tool most likely to be called first | mitigate | The lean projection: per-window muscle rollup instead of the weeks x 19 grid, no per-exercise frequency list, `weeks` capped at `MAX_SUMMARY_WEEKS` (12) rather than 52. Budget 16 KB enforced in plan 06-10 |
| T-06-09 | Repudiation / integrity of advice | dropping `RecompositionResult.disclaimer` while projecting the verdict into a flatter shape | mitigate | `recomposition_disclaimer` is a declared field of `TrainingSummaryResponse` copied verbatim from `recomposition.disclaimer`; plan 06-02 asserts it is in the model's `required` list and plan 06-11 asserts it is non-empty in a live response |
| T-06-14 | Repudiation (freshness) | reporting per-muscle numbers under `workouts`-only freshness, hiding a stale `exercise_templates` sync | mitigate | `freshness` is taken from the muscle-volume result (`FRESHNESS_RESOURCES_MUSCLE` — both resources), never from the weekly-volume result |
| T-06-01 | Information Disclosure | any of the four analytics calls raising | mitigate | `@safe_tool(degraded=_degraded_summary)`; detail to `log.exception` only |
| T-06-02 | Elevation of Privilege | `user_id` as a tool parameter | mitigate | `resolve_user_id(ctx)` server-side; the tool exposes only `ctx` and `weeks` |
| T-06-03 | Tampering | a write reaching the database | mitigate | Single `read_only_session` (`postgresql_readonly=True`) wrapping all four calls |
| T-06-13 | Denial of Service (latency) | ~seven aggregate queries against Claude's 10 s discovery / 30 s call budget | accept | Single user, ~8k sets; Phase 4 measured the core aggregate at ~50 ms. Recorded, and re-checked at the Phase 6 live smoke test rather than pre-optimized |
</threat_model>
