```bash
# DEPLOY-04: production ran a schema BEHIND the deployed code three separate times during v2.0 --
# Phase 8 (`alembic current` was 0004, the code needed 0005), the Phase 9 operator run (the
# shell was pointed at the wrong DATABASE_URL, so the before-state read was stale), and the
# Phase 13 spike (0005 vs 0006, surfacing in production as
# `UndefinedTableError: relation "user_program_history" does not exist`). Every one of those was
# a human forgetting to migrate, not a missing detector, so this step APPLIES the pending
# migrations (D-01) and then independently re-verifies that they landed (D-02) rather than
# trusting the upgrade command's exit code. `set -euo pipefail` at the top of this file is what
# turns any failure below into an abort BEFORE `exec gcloud run deploy` runs.
#
# D-05: the URL is fetched from Secret Manager here rather than inherited from the shell,
# because a wrong DATABASE_URL in an operator's environment is precisely what the Phase 9
# incident was. D-06: BRETT_DATABASE_URL is the deliberate escape hatch for testing this
# pipeline against a non-production database; leave it unset and the production path always
# resolves through `gcloud secrets versions access`. --project is pinned for the same reason it
# is pinned on the deploy below: the active gcloud project on a developer machine is routinely
# something unrelated.
#
# The value is passed per-command and never `export`ed, so it does not enter the environment of
# the gcloud invocation below, and it is never echoed. Never add `set -x` to this file: it would
# print the production DSN into the terminal and into any CI log capturing this deploy.
DATABASE_URL="${BRETT_DATABASE_URL:-$(gcloud secrets versions access latest --project="$PROJECT_ID" --secret="brett-database-url")}"

# An empty value here would make `alembic upgrade head` fail with a pydantic ValidationError
# about a missing field, which reads like a code bug rather than a missing secret.
if [[ -z "$DATABASE_URL" ]]; then
  echo "DEPLOY-04: DATABASE_URL resolved to an empty value; gcloud secrets versions access latest --secret=brett-database-url returned nothing and BRETT_DATABASE_URL is unset. Refusing to deploy." >&2
  exit 1
fi

# Which source was used, WITHOUT the value: migrating the wrong database is as bad as not
# migrating, and this line is the only record of which one this deploy touched.
if [[ -n "${BRETT_DATABASE_URL:-}" ]]; then
  echo "DEPLOY-04: using the BRETT_DATABASE_URL override (non-production path)"
else
  echo "DEPLOY-04: using Secret Manager brett-database-url:latest in project $PROJECT_ID"
fi

# D-01: apply, do not merely detect. alembic runs from backend/ because alembic.ini lives there,
# and via its own CLI for the same reason this script shells out to gcloud.
(cd "$REPO_ROOT/backend" && DATABASE_URL="$DATABASE_URL" uv run alembic upgrade head)

# D-02: an independent confirmation that `alembic current` now equals `alembic heads`. A partial
# or silently-incomplete apply exits 1 here and the deploy never happens. The predicate lives in
# backend/app/db/migration_preflight.py so backend/tests/test_migration_preflight.py can call it
# directly against a real drifted database (D-04).
(cd "$REPO_ROOT/backend" && DATABASE_URL="$DATABASE_URL" PYTHONPATH="$REPO_ROOT/backend" uv run python -m app.db.migration_preflight)
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Secret Manager → deploy script | The production DSN crosses into a local shell process on an operator's machine |
| deploy script → production database | The script now holds DDL authority: `alembic upgrade head` mutates the production schema |
| deploy script → terminal / CI log | Every line the script emits is captured somewhere durable |
| `BRETT_DATABASE_URL` env var → which database gets migrated | An operator-controlled input decides the blast radius |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Information disclosure | the `DATABASE_URL` variable inside `scripts/deploy-cloud-run.sh` | mitigate | The value is passed per-command (`DATABASE_URL="$DATABASE_URL" uv run …`) and never `export`ed, so it is absent from the gcloud invocation's environment; it is never echoed; `set -x` is forbidden. Enforced by `test_deploy_script_never_traces_or_exports_the_database_url`, which asserts the absence of `set -x`, `export DATABASE_URL` and any echo of the value |
| T-14-02 | Tampering / Elevation of privilege | `alembic upgrade head` running unattended against production on every deploy | mitigate | `alembic upgrade head` can only apply revisions already committed under `backend/migrations/versions/`, so the change set is whatever code review already saw; `test_migrations_round_trip` proves every revision reverses; the verification step aborts before `gcloud run deploy` if the apply was partial. Residual risk — a reviewed-but-destructive migration still runs — is documented with a pre-deploy review step in plan 14-03's runbook, backed by `docs/runbook-backup-restore.md` |
| T-14-03 | Spoofing | `BRETT_DATABASE_URL` pointing a "production" deploy at the wrong database, or an operator believing the override is off when it is on | mitigate | The override is opt-in and absent by default, so the production path always resolves through `gcloud secrets versions access latest --secret="brett-database-url"` with `--project="$PROJECT_ID"` pinned; the script prints WHICH source it used (never the value) so the deploy log records which database was migrated. Enforced by the `_MIGRATION_PREFLIGHT_MARKERS` and source-echo assertions |
| T-14-04 | Denial of service | an unreachable or wrong DSN now aborts every deploy | accept | Failing closed is the requirement (ROADMAP criterion 1). The abort names DEPLOY-04 and the remediation, and the empty-value guard converts the most confusing case (a silent secret miss reading as a pydantic ValidationError) into an explicit refusal |
| T-14-09 | Tampering | a future edit inserting the new block, or a comment about it, INSIDE the backslash-continued `exec gcloud run deploy` invocation | mitigate | The block is placed strictly above the invocation as plain statements; `test_deploy_script_has_no_comment_inside_the_gcloud_call` already fails the build on the comment variant, and the new `min(hits) < starts[0]` ordering assertion fails on the placement variant |
</threat_model>
