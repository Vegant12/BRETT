# Phase 1 Plan 03: Database Layer and Migrations Summary

SQLAlchemy 2.0 declarative layer with TIMESTAMPTZ enforced by a mixin, an async Alembic environment whose DSN never touches the committed `alembic.ini`, a two-revision migration chain that creates and seeds the single v1 user, and a test harness that builds every database from `alembic upgrade head` in a real Postgres 18 container.

## What Was Built

**Declarative layer** (`app/db/`). `Base` carries a `MetaData` with the five-key `NAMING_CONVENTION`, so autogenerated downgrades reference model-derived constraint names (`pk_users`) rather than server-assigned ones. `TimestampMixin` is the mechanism behind FOUND-04 — `created_at`/`updated_at` are `DateTime(timezone=True)` with `server_default=func.now()`, and `updated_at` also carries `onupdate=func.now()`. `User` is the only model: UUID PK, `timezone` `String(64)` with a `Asia/Jakarta` server default. `session.py` exposes `make_engine` (with `pool_pre_ping=True`, `echo=False`) and `make_sessionmaker` as factories — there is no module-level engine, which would bind its pool to whichever event loop imported it.

**Migrations.** `alembic.ini` has no `sqlalchemy.url` key at all; `migrations/env.py` injects the URL at runtime from `get_settings().async_database_url` with the required `%` → `%%` ConfigParser escape, sets `target_metadata = Base.metadata`, imports `app.db.models` so autogenerate actually sees the table, enables `compare_type`/`compare_server_default`, and uses `pool.NullPool`.

Final `0001` column list (autogenerated then hand-reviewed):

| Column | Type | Null | Server default |
|---|---|---|---|
| `id` | `UUID` | NOT NULL | — (PK `pk_users`) |
| `timezone` | `VARCHAR(64)` | NOT NULL | `'Asia/Jakarta'` |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | NOT NULL | `now()` |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | NOT NULL | `now()` |

`downgrade()` is `op.drop_table("users")`. `0002` inserts the fixed row `00000000-0000-0000-0000-000000000001` / `Asia/Jakarta` via `op.bulk_insert` on a lightweight `sa.table()` construct — the ORM model is never imported into a migration — and deletes it by bound parameter on downgrade.

**Test infrastructure** (`backend/tests/conftest.py`). Container image: **`postgres:18-alpine`**, started via `PostgresContainer("postgres:18-alpine", driver="asyncpg")` (the explicit driver is required; the default `psycopg2` is not a dependency of this project).

## Key Decisions

**Explicitly-typed UUID bind in the seed downgrade.** The plan's sample used `bindparams(uid=str(DEFAULT_USER_ID))`. SQLAlchemy infers VARCHAR from a `str` value, asyncpg then emits `DELETE FROM users WHERE id = $1::VARCHAR`, and Postgres rejects it with `operator does not exist: uuid = character varying`. The fix is `sa.bindparam("uid", DEFAULT_USER_ID, type_=postgresql.UUID(as_uuid=True))` — the type, not the value, is what asyncpg casts on.

**`DEFAULT_USER_ID` duplicated in conftest, not imported from `0002`.** A test that imports the very constant it asserts against proves nothing, and application/test code importing a migration module couples it to a historical revision.

**`restore_schema` fixture.** `test_migrations_round_trip` downgrades the session-scoped container. Without a `finally`-block restore, a mid-test failure leaves the shared database at `base` and every later container-backed test fails for an unrelated reason, hiding the real failure.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `0002` downgrade failed against Postgres**
- **Found during:** Task 2 round-trip verification
- **Issue:** `alembic downgrade base` raised `operator does not exist: uuid = character varying`. The plan's `bindparams(uid=str(...))` gives asyncpg an untyped VARCHAR bind.
- **Fix:** `sa.bindparam("uid", DEFAULT_USER_ID, type_=postgresql.UUID(as_uuid=True))`
- **Files modified:** `backend/migrations/versions/0002_seed_default_user.py`
- **Commit:** `5aaab0c`

**2. [Rule 3 - Blocking] Local Postgres container would not start**
- **Found during:** Task 2, before autogenerate
- **Issue:** `docker-compose.yml` (from Plan 01-01) mounts the volume at `/var/lib/postgresql/data`. `postgres:18` refuses to start with that layout — it stores data in a major-version subdirectory and wants the mount one level up. Without a database, no migration could be generated or verified.
- **Fix:** mount `brett_pgdata:/var/lib/postgresql`; added a `pg_isready` healthcheck so `docker compose up --wait` is deterministic.
- **Files modified:** `docker-compose.yml`
- **Commit:** `5aaab0c`

**3. [Rule 2 - Missing coverage] Added `backend/tests/test_db_models.py`**
- **Found during:** Task 1
- **Issue:** Task 1 is marked `tdd="true"` but the plan listed no test file, leaving the RED phase with nothing to fail against and the declarative-layer contract unasserted in CI.
- **Fix:** seven container-free tests covering the D-07 table set, TIMESTAMPTZ types, the Jakarta default, the UUID PK, the naming convention, the absence of ORM relationships, and `make_engine`'s `echo=False`/`pool_pre_ping` safety settings.
- **Files modified:** `backend/tests/test_db_models.py`
- **Commit:** `8115700`
