**The deploy mechanism (`scripts/deploy-cloud-run.sh`, unmodified — quoted so you need not open
it).** It resolves `DATABASE_URL` from Secret Manager (`brett-database-url:latest`) unless
`BRETT_DATABASE_URL` is set, refuses to deploy on a failed or empty resolution, echoes WHICH source
it used (never the value), then runs, in this fixed order:

    1. echo "DEPLOY-04: using Secret Manager brett-database-url:latest in project $PROJECT_ID"
    2. (cd backend && DATABASE_URL=... uv run alembic upgrade head)
    3. (cd backend && DATABASE_URL=... PYTHONPATH=... uv run python -m app.db.migration_preflight)
       -> prints `at head: ['0007']`, or aborts with `DEPLOY-04 violated: ...`
    4. exec gcloud run deploy brett --project=... --region=... --source=... --allow-unauthenticated
         --port=8080 --memory=1Gi --env-vars-file=deploy/cloud-run.env.yaml --set-secrets=... --quiet

`set -euo pipefail` is declared at the top of that script, so a failure at step 2 or 3 aborts BEFORE
step 4 and no new revision is created at all. There is no `--skip-migrations` flag and none may be
added.

**Migration 0007 is purely additive.** `backend/migrations/versions/0007_physique_observations.py`
is two `create_table` calls (`physique_observations`, `physique_ratings`) with no `alter_column`, no
`drop_*`, and no data migration. Per `docs/runbook-deploy.md` Step 3 it is therefore NOT a
"destructive revision", so no `docs/runbook-backup-restore.md` backup gate applies before this
deploy (19-RESEARCH.md Assumptions Log A4).

**The MCP read tool's response contract** — `backend/app/mcp/tools/schemas.py:707-722`,
`class LatestPhysiqueObservationResponse`:

    data_available: bool
    observation: PhysiqueObservationView | None
    rating_scale: str
    disclaimer: str

Its docstring states: "`observation=None` with `data_available=True` means the user has never logged
one -- a different fact from `data_available=False`, which means the server could not look."
Production has never had a physique observation logged (the write tool did not exist in any deployed
revision before this phase), so the EXPECTED and PASSING smoke-test result is:

    {"data_available": true, "observation": null, "rating_scale": "<non-empty>", "disclaimer": "<non-empty>"}

`observation: null` is a PASS, not an inconclusive result (19-RESEARCH.md Pitfall 4). Do NOT call the
write tool `fitness_log_physique_observation` to "really" prove the read tool works — that writes
real data into production for a phase whose job is verification, not data creation.

**The proven JSON-RPC envelope for the live endpoint**, adapted from `docs/runbook-secret-rotation.md`
Step 6 — the only invocation in this repo verified (2026-09-01) against this exact production
service. `params._meta` is MANDATORY: omit it and the server answers `-32602` inside a 200, which
would make the whole assertion meaningless.

```bash
BASE="$(gcloud run services describe brett --project=brett-fitness \
          --region=us-central1 --format='value(status.url)')"
MCP_HDRS=(-H 'Accept: application/json, text/event-stream'
          -H 'Content-Type: application/json'
          -H 'MCP-Protocol-Version: 2026-07-28'
          -H 'Mcp-Method: tools/call'
          -H 'Mcp-Name: fitness_get_latest_physique_observation')
MCP_BODY='{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"fitness_get_latest_physique_observation","arguments":{},"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}'
curl -sS -X POST "$BASE/mcp" "${MCP_HDRS[@]}" -H "Authorization: Bearer $TOKEN" --data "$MCP_BODY" \
| python3 -c '
import json,sys
raw=sys.stdin.read()
if raw.lstrip().startswith("data:"):
    raw="\n".join(l[6:] for l in raw.splitlines() if l.startswith("data: "))
print(json.dumps(json.loads(raw), indent=2))'
```

Note the correction recorded in `docs/runbook-secret-rotation.md` ("Two corrections to the
prescribed commands"): this deployment answered `application/json`, not `text/event-stream`, so a
bare `sed -n 's/^data: //p'` emits nothing and the JSON parse fails on empty input. The snippet
above tolerates both shapes. This curl path is usable ONLY in `static` auth mode — i.e. only on
Task 4's fallback route B.
