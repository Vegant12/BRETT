**Intro paragraph.** This runs **once**, maybe twice, ever. It imports the Apple Health history
that predates the webhook — the file the user exported by hand from the Health app — through the
same normalizer and the same upsert the live webhook uses, so a day covered by both holds one value
per metric rather than two. It is a **local** command run against the production database, not a
deployed job: the file is 191 MB on the operator's own machine, Cloud Run caps a request body at
32 MiB, and a Cloud Run Job would mean uploading gitignored health data to Cloud Storage for a
command that runs once (D-01).

**Sub-section "Before you run it".** A numbered pre-flight list:

1. Confirm the file is where you think it is and is the export you mean:
   ```bash
   ls -l export.xml
   head -c 400 export.xml | grep -o 'ExportDate value="[^"]*"'
   ```
2. Confirm the production database is not behind the deployed code. This has been the failure mode
   **twice** (see `docs/runbook-sync-schedule.md`), and this command writes to
   `health_daily_metrics`, which migration `0005` created:
   ```bash
   DATABASE_URL='<production-database-url>' uv run alembic current
   DATABASE_URL='<production-database-url>' uv run alembic heads
   # These must match. If they do not: DATABASE_URL='<...>' uv run alembic upgrade head
   ```
3. Note what is already in the table, so you can tell afterwards what the backfill added:
   ```sql
   SELECT source, count(*), min(local_day), max(local_day)
   FROM health_daily_metrics
   GROUP BY source;
   ```

```bash
# zsh/bash when HIST_IGNORE_SPACE / HISTCONTROL=ignorespace is set.

```

Then a table of the figures to check the printed summary against — copy the "Expected `--dry-run`

**Sub-section "Step 2 — the real run".**

```bash
 DATABASE_URL='<production-database-url>' PYTHONPATH=backend \
   uv run python -m app.cli backfill-apple-health export.xml --write
```

State that `--dry-run` and `--write` are mutually exclusive and one of them is **required** — a
forgotten flag is an argparse error, never a silent full write. State the expected runtime shape:
the parse is a few seconds; the write is the slow part and its speed is the round-trip latency to
the database, so a `health_backfill_progress` line appears roughly every 500 rows (about 16 lines
for a full run). Silence for minutes with no progress line means the connection, not the parser.

**Sub-section "Afterwards".** Verification queries, as SQL blocks:

```sql
-- 1. What landed, and over what span.
SELECT source, count(*) AS rows, min(local_day), max(local_day)
FROM health_daily_metrics
GROUP BY source;

-- 2. Success criterion #3: no metric-day may hold two rows for the SAME source_name.
SELECT metric, source_name, local_day, count(*)
FROM health_daily_metrics
GROUP BY 1, 2, 3
HAVING count(*) > 1;
-- Expect ZERO rows. Two rows for the same metric-day with DIFFERENT source_name values is
-- correct and expected (two phones, two nutrition apps); two with the SAME one is the bug.

-- 3. Success criterion #4: no Hevy-sourced row may exist.
SELECT count(*) FROM health_daily_metrics WHERE lower(source_name) = 'hevy';
-- Expect 0.

-- 4. Freshness bookkeeping advanced for both resources.
SELECT resource, status, last_synced_at
FROM sync_state
WHERE provider = 'apple_health';
```

**Sub-section "If something goes wrong".**
- One bad row is skipped and logged as `health_backfill_row_skipped` (metric, day, source name and
  the exception's class name — never a value); the run continues. Re-running the command is safe
  and is a no-op on rows that already landed correctly.
- A malformed XML element is counted as `malformed` on the `records:` line and skipped; the run
  continues to the end of the file (D-07).
- An unreadable or non-HealthKit file exits 1 with
  `Apple Health backfill failed: Apple Health export file could not be read as a HealthKit export`
  and writes nothing.
- The whole command is idempotent by construction: replace semantics on the natural key
  `(user_id, source, metric, source_name, local_day)`. Running it twice produces the same table.

**Credential hygiene, stated once and plainly:** every `DATABASE_URL` in this section is the

a commit message, or into a chat transcript. `gitleaks` runs in pre-commit and will refuse the
commit, but the rule is the point, not the hook.
