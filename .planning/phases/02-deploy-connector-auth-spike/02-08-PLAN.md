`model_config` sets `extra="ignore"`. A typo'd key in the env file is therefore silently dropped at
deploy time - that silence is the entire reason the drift test exists.

The helper to port **verbatim** from `backend/tests/test_render_blueprint.py` (lines 41-55). It is
load-bearing: `MCP_ALLOWED_HOSTS` is reached through `validation_alias`, not by lowercasing the
field name, so a naive name check reports a false drift on the one variable a `421` depends on.

```python
def _settings_env_names() -> set[str]:
    names: set[str] = set()
    for name, field in Settings.model_fields.items():
        names.add(name.upper())
        alias = field.validation_alias
        if isinstance(alias, str):
            names.add(alias.upper())
    return names
```

`REPO_ROOT = Path(__file__).resolve().parents[2]` is the established idiom for reaching a repo-root
file from `backend/tests/` (`test_config.py:12`, `test_render_blueprint.py:26`).

Verified `gcloud` semantics (SDK 578.0.0, quoted from `gcloud run deploy --help`):
- `--env-vars-file=FILE_PATH` - *"All existing environment variables will be removed before the new
  environment variables are added."* The file is therefore the complete non-secret environment.
- `--set-secrets` - *"All existing secrets will be removed first."* Same completeness rule.
- `--env-vars-file` and `--set-secrets` sit in separate mutually-exclusive groups, so they compose.
  A key bound in **both** is rejected by Cloud Run.
- `--min=MIN` is a **service**-level setting, modifiable without deploying a new revision;
  `--min-instances` is revision-level and gcloud's own help steers you to `--min`.
- `--source` prefers a `Dockerfile` if one is present, otherwise Cloud Buildpacks. Do **not** add a
  Dockerfile pre-emptively - it would silently override buildpacks.

Verified Cloud Buildpacks behaviour (source read of `GoogleCloudPlatform/buildpacks` @ main):
- uv is selected when `pyproject.toml` **and** `uv.lock` both exist at the source root and
  `requirements.txt` does not. Both conditions hold in this repo.
- The buildpack runs a bare `uv sync` - **no `--frozen`, no `--no-dev`**.
- `google.config.entrypoint` opts in only if `GOOGLE_ENTRYPOINT` is set, a `Procfile` exists, or an
  `app.yaml` entrypoint exists. This repo has none, so the build falls through to
  `google.python.missing-entrypoint`, which looks for `main.py`/`app.py` **at the source root**,
  finds neither, and fails with:
  `for Python with pyproject.toml, provide a main.py or app.py file ...`
- `ctx.AddProcess` wraps every process as `bash -c "<command>"`, so `$PORT` in a `Procfile` expands.

**1. `Procfile`** - repo root. Exactly one line, **no comments** (the CNB Procfile parser is not a
place to experiment):

```
web: uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port $PORT
```

Three details make this correct rather than merely plausible. `--app-dir backend` is required
because `uv.lock` records the root project as `source = { virtual = "." }`, so `uv sync` installs
dependencies only and never puts `backend/` on `sys.path` - without the flag the container dies
with `ModuleNotFoundError: No module named 'app'`, remotely and silently. `--host 0.0.0.0` is
required by Cloud Run's container contract (*"the ingress container should not listen on
127.0.0.1"*). `$PORT` expands because buildpacks wrap the process in `bash -c`. There is
deliberately no `uv run` prefix: the uv buildpack prepends its venv's `bin` to `PATH` in the layer's
shared environment, so `uvicorn` is already on `PATH` at launch.

**4. `scripts/deploy-cloud-run.sh`** - new `scripts/` directory, mode `0755`:

```bash
#!/usr/bin/env bash
# The single reproducible description of how BRETT deploys (D-06e). This replaces
# render.yaml: it is what a future reader opens to learn how this service reaches
# production, and backend/tests/test_cloud_run_deploy.py asserts every flag below
# is still here.
#
# Requires: gcloud >= 578, an authenticated account, and the project bootstrap
# performed by plan 02-05 (APIs enabled, runtime service account, secrets created).
set -euo pipefail

REPO_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"

# Never inherit `gcloud config get-value project`: the active project on a
# developer machine is routinely something unrelated, and a silent deploy into the
# wrong project is expensive to notice.
PROJECT_ID="${BRETT_GCP_PROJECT:?set BRETT_GCP_PROJECT}"
REGION="${BRETT_GCP_REGION:-us-central1}"
SERVICE="${BRETT_SERVICE:-brett}"
# D-06f: 0 while proving the pipeline, 1 before any real connector test. Prefer
# flipping it with `gcloud run services update SERVICE --min=1`, which is a
# service-level change and needs no rebuild.
MIN_INSTANCES="${BRETT_MIN_INSTANCES:-0}"
# Bounds total Postgres connections: SQLAlchemy holds at most 10 per instance.
MAX_INSTANCES="${BRETT_MAX_INSTANCES:-2}"
RUNTIME_SA="brett-run@${PROJECT_ID}.iam.gserviceaccount.com"

exec gcloud run deploy "$SERVICE" \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --source="$REPO_ROOT" \
  --service-account="$RUNTIME_SA" \
  --allow-unauthenticated \
  --port=8080 \
  --min="$MIN_INSTANCES" \
  --max="$MAX_INSTANCES" \
  --cpu-boost \
  --memory=512Mi \
  --timeout=300 \
  --env-vars-file="$REPO_ROOT/deploy/cloud-run.env.yaml" \
  --set-secrets="DATABASE_URL=brett-database-url:latest,MCP_AUTH_SECRET=brett-mcp-auth-secret:latest" \
  --set-build-env-vars="UV_FROZEN=1,UV_NO_DEV=1" \
  --quiet
```

`--allow-unauthenticated` is required, not lax: Claude's connectors cannot mint a Google ID token,
so Cloud Run's IAM invoker check must be off and the MCP `TokenVerifier` is the real gate. Auth
Verification Matrix rows 1-3 in plan 02-05 are what prove the service is not actually open.
