<interfaces>
**D-06f cutover checklist**, the Cloud Run replacement for the abandoned Render free-to-Starter
upgrade. Same trigger point, same purpose, different mechanism:

1. Flip `MCP_AUTH_MODE` to `authkit` and fill `MCP_ISSUER_URL` / `MCP_JWKS_URI` in
   `deploy/cloud-run.env.yaml`, then redeploy with `./scripts/deploy-cloud-run.sh`
2. `gcloud run services update brett --project="$PROJECT_ID" --region="$REGION" --min=1`
3. Confirm the service no longer cold-starts after an idle period
4. Re-run Auth Verification Matrix rows 1-7 against the cut-over service **before** adding the
   connector

**Use `--min`, not `--min-instances`.** Verified from `gcloud run deploy --help`, SDK 578.0.0:

| Flag | Scope | Behaviour |
|---|---|---|
| `--min=MIN` | **Service** | *"divided among all Revisions receiving a percentage of traffic and can be modified without deploying a new Revision"* |
| `--min-instances=MIN` | Revision | *"immutably set on each new Revision and modifying its value will deploy another Revision. Consider using `--min` ..."* |

So the flip is instant, needs no rebuild, and is reversible in seconds:
`gcloud run services update brett --project="$PROJECT_ID" --region="$REGION" --min=0`.

Google is honest that minimum instances are *"a best-effort target to keep instances warm and
ready"* — residual risk is infrastructure rebalancing, crashes, and capacity exhaustion. For a
one-user personal service that is a non-issue. What it does not remove is Neon's own 5-minute
autosuspend wake (~0.3-0.5 s) on the first query after idle — irrelevant to the 10-second discovery
probe, which never touches the database.

**Claude's discovery sequence**, which the connector will drive:
1. `POST /mcp` with no token → our `401` carrying
   `resource_metadata="https://<host>/.well-known/oauth-protected-resource/mcp"`
2. `GET` that metadata → `{"resource": "https://<host>/mcp", "authorization_servers": ["https://<project>.authkit.app"]}`
3. `GET https://<project>.authkit.app/.well-known/oauth-authorization-server` (RFC 8414)
4. CIMD or DCR client identification
5. Authorization Code + PKCE(S256) + `resource=<mcp url>`, redirect to `https://claude.ai/api/mcp/auth_callback`
6. Token endpoint → JWT with `aud` = the Resource Indicator
7. Retry `POST /mcp` with `Authorization: Bearer <jwt>` → 200

Hard timing constraint: Claude allows **10 seconds** for discovery, registration and token
endpoints (30 s for refresh). `authorization_servers[0]` wins and Claude does not fall back to later
entries; the SDK emits a single-entry list by construction.

Free, Pro and Max Claude plans can all add custom connectors (Settings → Connectors → "Add custom
connector", with optional OAuth credentials under Advanced settings).

**Pitfall CR-3, which this plan is exposed to twice.** `--env-vars-file` and `--set-secrets` each
remove everything they do not list. Only ever change configuration by re-running
`scripts/deploy-cloud-run.sh`; never patch the live service with a one-off `--set-env-vars`, which
would wipe `DATABASE_URL` and 500 the next request.
