<objective>
Persist Hevy workouts idempotently and drive the full historical sync that fills an empty
database.

Purpose: this is the plan where HEVY-01, HEVY-03 and HEVY-08 actually happen. Hevy's child
objects have **no ids** — only an `index` — so a workout's exercises and sets cannot be upserted
individually. The only correct shape is: upsert the parent on
`(user_id, provider, external_id)`, then delete and reinsert all of its children. Per-child
upserts by `(workout_id, index)` look reasonable and are wrong: an edited workout with *fewer*
sets leaves the surplus rows behind, silently inflating every Phase 4 volume figure.

Output: `backend/app/integrations/hevy/workouts.py` with the persistence primitives and the
full-sync driver, plus integration suites for the happy path and the failure paths.
</objective>

Module docstring:
```python
"""Workout persistence and full sync (HEVY-01, HEVY-03, HEVY-08).

Idempotency has a specific shape here, forced by the API: Hevy's exercises and sets carry only
an `index`, never an id. There is therefore no stable key to upsert a child against. The
correct pattern -- verified against PostgreSQL 18 -- is:

    upsert the workout on (user_id, provider, external_id)
    DELETE its exercises  (ON DELETE CASCADE takes the sets)
    reinsert every exercise and set

The tempting alternative -- upsert children on (workout_id, index) -- is wrong in a way that
is invisible until Phase 4: an edited workout with FEWER sets than before leaves the surplus
rows in place, and every volume, tonnage and PR figure computed from them is inflated forever.

Failure isolation uses SAVEPOINTs, not try/except alone. In PostgreSQL a failed statement
aborts the whole transaction; every later statement then fails with "current transaction is
aborted, commands ignored until end of transaction block". `session.begin_nested()` is what
makes "skip the one bad workout, commit the other nine" possible at all.
"""
```

  end_time=workout.end_time, provider_created_at=workout.created_at,

  `.returning(Workout.id)` and `scalar_one()`.
- Add this comment above the `on_conflict_do_update`:
  ```python

    # RETURNING emit NOTHING, which makes scalar_one() raise NoResultFound on exactly the
    # workouts that were skipped as unchanged (Pitfall 4). Hevy is the source of truth and an
    # unconditional update is always correct here; the guard would buy nothing and cost a
    # branch that only fires in production.
  ```

- Then replace the children:
  ```python
    # Delete-and-reinsert, NOT per-child upsert. See the module docstring.
    # ON DELETE CASCADE on workout_sets.workout_exercise_id removes the sets.
    await session.execute(
        delete(WorkoutExercise).where(WorkoutExercise.workout_id == workout_id)
    )
    for exercise in workout.exercises:
        exercise_id = uuid.uuid4()
        await session.execute(insert(WorkoutExercise).values(
            id=exercise_id, workout_id=workout_id, exercise_index=exercise.index,
            title=exercise.title, notes=exercise.notes,
            exercise_template_external_id=exercise.exercise_template_id,
            supersets_id=exercise.supersets_id,
        ))
        if exercise.sets:
            # executemany: a list of dicts as the SECOND argument to session.execute().
            # Measured at 44x faster than row-by-row for 12,000 rows; `sets` is by far the
            # highest-cardinality table this sync writes.
            await session.execute(insert(WorkoutSet), [
                {"id": uuid.uuid4(), "workout_exercise_id": exercise_id,
                 "set_index": s.index, "set_type": s.type, "weight_kg": s.weight_kg,
                 "reps": s.reps, "distance_meters": s.distance_meters,
                 "duration_seconds": s.duration_seconds, "rpe": s.rpe,
                 "custom_metric": s.custom_metric}
                for s in exercise.sets
            ])
    return workout_id
  ```

**`async def delete_workout(session, *, user_id: uuid.UUID, external_id: str) -> bool`**
```python
    """Delete a workout and (by FK cascade) everything under it. HEVY-04.

    Returns False when nothing matched. That is a NO-OP, not an error: the events feed can
    report a deletion for a workout that was created and deleted between two of our syncs and
    that we therefore never stored.
    """
    result = await session.execute(
        delete(Workout).where(
            Workout.user_id == user_id,
            Workout.provider == PROVIDER,
            Workout.external_id == external_id,
        )
    )
    return bool(result.rowcount)
```

**`async def persist_workout_page(session, *, user_id, workouts: Sequence[HevyWorkout]) -> PagePersistResult`**
```python
    upserted = 0
    skipped: list[str] = []
    for workout in workouts:
        try:
            async with session.begin_nested():   # SAVEPOINT
                await upsert_workout(session, user_id=user_id, workout=workout)
        except SQLAlchemyError as exc:
            # Class name only. `str(exc)` on a DataError renders the offending parameter
            # values -- i.e. this user's workout titles and weights -- straight into a log
            # line (T-03-23).
            skipped.append(workout.id)
            log.warning("hevy_workout_skipped", workout_id=workout.id,
                        reason=type(exc).__name__)
        else:
            upserted += 1
    return PagePersistResult(upserted=upserted, skipped=tuple(skipped))
```

and `DBAPIError`. Do **not** catch bare `Exception`: a `HevyError` or a `CancelledError` must

Add to `backend/app/integrations/hevy/workouts.py`:

```python
async def sync_workouts(
    client: HevyClient,
    sessionmaker: async_sessionmaker[AsyncSession],
    *,
    user_id: uuid.UUID,
) -> WorkoutSyncResult:
    """Full historical sync of `/v1/workouts` (HEVY-01, D-08).

    Commits PER PAGE, with the resume checkpoint written in the SAME transaction as that
    page's rows. Two separate transactions could interleave into a checkpoint that claims
    work which was then rolled back -- the checkpoint would say "resume at page 12" over a
    database that only holds eleven pages.

    Per-page commit is not an optimisation, it is HEVY-08: Hevy caps pageSize at 10, so a full
    history is dozens to hundreds of sequential requests, and one transaction for the whole
    run would discard every page of work on a transient failure at page 40.
    """
```

Implementation, in this exact order:

1. **Open the run.** In its own short transaction:
   `state = await ensure_sync_state(session, user_id=user_id, provider=PROVIDER,
   resource=RESOURCE_WORKOUTS)`; `start_page = state.cursor_page or 1`;
   `await mark_running(...)`; `await session.commit()`.
   Log `log.info("hevy_workout_sync_started", start_page=start_page)`.

2. **Wrap steps 3-6 in `try/except`.** On any `Exception`, open a fresh session, call
   `record_sync_error(session, ..., exc=exc)`, commit, log
   `log.warning("hevy_workout_sync_failed", reason=type(exc).__name__)`, and **re-raise**.
   Comment: `# The cursors are deliberately NOT reset here: leaving cursor_page in place is`
   `# what makes the next run resume instead of restarting from page 1 (D-08).`

3. **Cheap reconciliation baseline.** `remote_count = await client.get_workout_count()`.
   Comment: `# One request. Turns "did the sync get everything?" from a hope into an`
   `# assertion, and is the cheapest available detector for the deletion drift D-09 accepts.`

4. **Page loop:**
   ```python
   page = start_page
   pages_fetched = 0
   upserted = 0
   skipped: list[str] = []
   while True:
       payload = await client.get_workouts(page=page)
       pages_fetched += 1
       async with sessionmaker() as session:
           result = await persist_workout_page(
               session, user_id=user_id, workouts=payload.workouts)
           await advance_cursor_page(session, user_id=user_id, provider=PROVIDER,
                                     resource=RESOURCE_WORKOUTS, cursor_page=page + 1)
           await session.commit()          # page rows + checkpoint, atomically
       upserted += result.upserted
       skipped.extend(result.skipped)
       log.info("hevy_workout_page_committed", page=page,
                page_count=payload.page_count, upserted=result.upserted,
                skipped=len(result.skipped))
       if not payload.workouts or page >= payload.page_count:
           break
       page += 1
   ```
   Add a comment on the loop condition:
   ```python
       # Offset pagination over mutating data: if Hevy orders newest-first, a workout logged
       # mid-sync shifts items toward later pages and one can be seen twice. That is harmless
       # -- the upsert is idempotent. Additions cannot cause a SKIP in either ordering; only a
       # mid-sync deletion can, and deletions are the events feed's job (D-09).
   ```

5. **Close the run.** In a fresh session: count local rows
   (`select(func.count()).select_from(Workout).where(user_id, provider)`), then
   `complete_sync(session, ..., last_synced_at=utc_now(), cursor_page=None)` and commit.
   If `remote_count is not None and local_count != remote_count`, log
   `log.warning("hevy_workout_count_mismatch", local=local_count, remote=remote_count)` —
   **do not raise**: a mismatch is information, and failing the run would leave a perfectly
   good sync marked as an error.

6. Log `log.info("hevy_workout_sync_completed", pages=pages_fetched, upserted=upserted,
   skipped=len(skipped), local_count=local_count)` and return `WorkoutSyncResult(...)`.

The function takes an `async_sessionmaker`, never an engine and never `Settings` — the caller
owns the engine's lifetime (`backend/app/db/session.py` documents why).
