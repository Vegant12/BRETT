<objective>
Create the five reference tables the sync service writes into besides workouts — exercise
templates, the curated muscle mapping, the manual-override layer, body measurements, and the
per-resource sync bookkeeping — plus the repository that reads and advances the bookkeeping.

Purpose: HEVY-09 requires each data source to expose its own `last_synced_at`, and this phase has
three independent sources with three independent cursors. D-08 needs a resume checkpoint that
commits inside the same transaction as the page it describes. D-04 needs the override layer to be
a separate table so the source mapping is never mutated and NORM-02's audit is free.

Explicitly **not** built: `external_connections.encrypted_credentials`. `Settings.hevy_api_key`
is already a `SecretStr` wired into all three redaction layers, and the blueprint sanctions an
env-var secret for a single-user personal deployment. Adding a decryptable credential column
would put a secret one SQL query away from the MCP server for zero v1 benefit. The table is named
`sync_state`, not `external_connections`, so the name cannot imply credential storage it
deliberately does not do.
</objective>

```python
"""Exercise templates and the muscle mapping layered on them (HEVY-06, NORM-02, NORM-03).

Three tables, deliberately:

* ``exercise_templates`` stores Hevy's RAW muscle-group strings verbatim. It is the audit
  baseline -- NORM-02 requires an override be checkable against "the original source mapping",
  and that is only possible if the original survives untouched.
* ``exercise_muscles`` is the CANONICAL derived mapping (D-02): Hevy's flat taxonomy translated
  and the deltoid/oblique splits applied. Recomputed from ``app.normalization`` on every
  template sync.

  above. Resolution is per-TEMPLATE replacement, not per-row merge -- a per-row merge would let
  a user add or change a muscle but never REMOVE one, so "this exercise does not actually work
  rear delts" would be unexpressible.

Neither table stores the direct/indirect WEIGHT. NORM-03 and blueprint §18 both require it be
configurable at query time; a weight column would freeze one answer into the data.
"""
```

**`backend/app/db/models/body.py`** — docstring:
```python
"""Body measurements (HEVY-07, D-06, D-07-corrected).

ONE table for every source, with a `source` discriminator, so weight and composition trends
are queried from one place regardless of origin. Manual entry is a later phase; the column
exists now so that phase needs no migration.

The natural key is `(user_id, source, measured_on)` -- the whole ROW, not one row per metric.
D-07's fallback assumed per-metric keying; the live API disproves it. Hevy's
`/v1/body_measurements` returns one object per calendar date carrying all 17 metrics and has
NO id field at all; its sibling endpoints (`GET/PUT /v1/body_measurements/{date}`, and a POST
that 409s if an entry exists for that date) confirm the date IS the identity.

`measured_on` is a `Date`, not a TIMESTAMPTZ. Hevy's field is `format: date`; storing a
timestamp would require inventing a time of day. This does not violate FOUND-04 -- a calendar
date is not an instant.
"""
```

**`backend/app/db/models/sync_state.py`** — docstring:
```python
"""Per-resource sync bookkeeping (HEVY-09, D-08).

One row per (user, provider, resource). Three resources exist in this phase -- workouts,
exercise_templates, body_measurements -- with three genuinely independent cursors, so a single
`last_synced_at` on a connections table could not answer HEVY-09 honestly.

Named `sync_state`, NOT `external_connections`. Blueprint §5.2's name implies the encrypted
credential storage this table deliberately does not do: `Settings.hevy_api_key` stays the
env-var secret, and a decryptable credential column would sit one SQL query away from the MCP
server for no v1 benefit.

`last_error` stores an exception CLASS NAME (plus a curated safe message where the exception
provides one), never a response body -- a Hevy error body can echo the request, headers
included.
"""
```
`class SyncState(Base, TimestampMixin)`, `__tablename__ = "sync_state"`:

```python
def format_sync_error(exc: BaseException) -> str:
    """Render an exception for storage WITHOUT leaking a payload.

    Only exceptions that opt in -- by exposing a `safe_message` attribute the raiser curated
    -- contribute any detail. Everything else stores its class name alone. This matters
    concretely: `pydantic.ValidationError.__str__` renders `input_value=...`, so a naive
    `str(exc)` would write a user's workout titles and body-composition numbers into a
    column and, from there, into any log line that reads it back (T-03-13).
    """
    detail = getattr(exc, "safe_message", None)
    if isinstance(detail, str) and detail:
        return f"{type(exc).__name__}: {detail}"[:_MAX_ERROR_LEN]
    return type(exc).__name__[:_MAX_ERROR_LEN]
```
