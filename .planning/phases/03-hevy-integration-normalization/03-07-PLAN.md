<objective>
Sync Hevy's exercise templates and turn them into a canonical, overridable muscle mapping.

Purpose: per-muscle analytics (Phase 4's VOL-02) structurally cannot exist without this. Hevy
supplies a primary and secondary muscle group per template — but its taxonomy has one flat
`shoulders` bucket, so NORM-01's front/side/rear split has to be applied here, from the curated
tables plan 03-03 authored. NORM-02 then needs the override to be *auditable against the original
source mapping*, which is only possible because `exercise_templates` keeps Hevy's raw strings and
the override lives in its own table that never mutates the derived one.

Output: `backend/app/integrations/hevy/templates.py` (transport-adjacent sync) and
`backend/app/normalization/resolver.py` (provider-neutral effective-mapping queries), each with
an integration suite.

Module docstring:
```python
"""Exercise-template sync and muscle-map materialisation (HEVY-06, NORM-01, NORM-03).

Two things happen per template, and keeping them separate is the point:

* ``exercise_templates`` stores Hevy's RAW ``primary_muscle_group`` and
  ``secondary_muscle_groups`` verbatim. That is the audit baseline NORM-02 compares an
  override against, and it is the only record of what Hevy actually said if Hevy later
  recategorises the exercise.
* ``exercise_muscles`` stores the CANONICAL result of running that raw data through
  ``app.normalization`` -- Hevy's flat ``shoulders`` expanded into the deltoid head(s) the
  movement actually trains. It is a materialised view of curated code (D-02), recomputed on
  every template sync, never hand-edited.

``/v1/exercise_templates`` caps ``pageSize`` at **100**, not 10 like every other endpoint in
this integration. Using 10 here would issue roughly 40 requests instead of 5 against a rate
limit Hevy has never documented (Pitfall 6).
"""
```

**`async def replace_exercise_muscles(session, *, user_id, template) -> int`**
```python
    """Recompute this template's canonical mapping from `app.normalization` (D-02).

    Delete-and-reinsert, exactly like workout children and for the same reason: a curated
    change that REMOVES a muscle must actually remove it. An upsert-only strategy could add
    and modify but never delete, so a correction like "this does not really work rear delts"
    would be silently ignored and the wrong row would live forever.

    Returns the number of assignment rows written -- zero is a valid, expected answer (D-03).
    """
    assignments = derive_assignments(
        template_id=template.id,
        title=template.title,
        primary_muscle_group=template.primary_muscle_group,
        secondary_muscle_groups=template.secondary_muscle_groups,
    )
    await session.execute(
        delete(ExerciseMuscle).where(
            ExerciseMuscle.user_id == user_id,
            ExerciseMuscle.exercise_template_external_id == template.id,
        )
    )
    if not assignments:
        return 0
    await session.execute(insert(ExerciseMuscle), [
        {"id": uuid.uuid4(), "user_id": user_id,
         "exercise_template_external_id": template.id,
         "muscle_group": a.muscle_group.value, "role": a.role.value,
         "source": a.source.value}
        for a in assignments
    ])
    return len(assignments)
```

Module docstring:
```python
"""Effective muscle mapping: curated base overridden by manual corrections (NORM-02, NORM-03).

**The resolution rule, and it is not the obvious one.** If ANY override row exists for a
template, the override set REPLACES the base set entirely. If none exists, the base applies.

A per-row merge -- the intuitive design -- would let a user add a muscle or change a role but
never REMOVE one, so the most common correction there is ("this exercise does not actually
work rear delts") would be unexpressible. Replacement also makes NORM-02's audit trivial: both
sets survive intact in their own tables and are diffable side by side, which is exactly what
"auditable against the original source mapping" asks for.

Provider-neutral by construction: this module imports nothing from ``app.integrations``. A
second provider writes the same tables and gets the same resolution for free.

NORM-03: the direct/indirect WEIGHT is applied here, at query time, by ``apply_weights`` --
never stored. Phase 4 passes its own mapping to answer "what if indirect counted 0.3?" without
a migration.
"""
```

Implementation notes to follow exactly:
- `effective_muscles` = `effective_muscles_bulk(...)[template_external_id]` (with `[]` default),
  so there is exactly one implementation of the rule.
- `effective_muscles_bulk`: one `select(ExerciseMuscleOverride.exercise_template_external_id,
  .muscle_group, .role).where(user_id ==, external_id.in_(ids))` and one equivalent
  `select` over `ExerciseMuscle` including `.source`. Group both by template id. For each
  requested id: if it has any override rows, emit those with
  `source=MappingSource.OVERRIDE`; otherwise emit the base rows with
  `MappingSource(row.source)`. Templates with neither get `[]`.

  `MuscleRole(value)`. If a stored value is not a member of the enum (a taxonomy change landed
  without a data migration), raise `ValueError` naming the column and value **but not the
  user** — that is a real integrity problem and must not be swallowed.
- None of these functions call `session.commit()`.
- Ordering: sort the returned list by `(role, muscle_group)` with `DIRECT` first, so tests and
  Phase 4 output are deterministic.
