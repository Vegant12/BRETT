- Header name: `Authorization`

**3. Required settings — the table.** Present as a table with a Why column:

| Setting | Required value | Why |
|---|---|---|
| Automation type | REST API | The only mode that POSTs JSON to a URL |
| Aggregation interval | **Daily** | **Correctness prerequisite.** BRETT stores one row per metric per source per local day and uses REPLACE semantics on re-send. With a daily interval each metric emits one datapoint per day, so a batch boundary can only fall *between* days. At any finer interval a day can be split across two POSTs and the second silently overwrites the first. It also shrinks the payload by roughly two orders of magnitude |
| Batch Requests | Off | With a daily interval the payload is small, so batching buys nothing and reintroduces the split-day risk above |
| Data type | Health Metrics | Workouts are deliberately not ingested (D-02) |
| Export period / window | A rolling window of several days (e.g. 7) | Overlap is safe and desirable: re-sending is a no-op (HEALTH-09), and it lets a missed run self-heal |
| Schedule | Hourly, or on-arrival | The endpoint has its own rate-limit bucket sized for this |

**4. Metrics to select** — reproduce the 12-row table from `<interfaces>` verbatim, including the
UI label column, and state that BRETT silently ignores anything else (D-04): an unlisted metric
