```python
MAX_TRUSTED_REPS = 12
E1RM_EXERCISE_TYPE = "weight_reps"

class NoEstimateReason(StrEnum):
    MODALITY = "modality_not_weight_reps"
    REP_RANGE = "reps_above_trusted_range"
    MISSING_OPERAND = "missing_weight_or_reps"

def estimate_1rm(*, weight_kg, reps, exercise_type):
    if exercise_type != E1RM_EXERCISE_TYPE:
        return None, NoEstimateReason.MODALITY
    if weight_kg is None or reps is None:
        return None, NoEstimateReason.MISSING_OPERAND
    if reps < 1 or reps > MAX_TRUSTED_REPS:
        return None, NoEstimateReason.REP_RANGE
    return (weight_kg * (Decimal(1) + Decimal(reps) / Decimal(30))).quantize(Decimal("0.001")), None
```
A session with `reps > 12` (real weight, real reps, `exercise_type="weight_reps"`) gets
`NoEstimateReason.REP_RANGE`: `best_e1rm_kg` is `None` but `best_weight_kg` is a real value. Per
`test_null_estimate_session_neither_extends_nor_breaks` (existing test, `progression.py`'s
`scan_plateau`), such a session is SKIPPED by the streak scan — it neither extends nor breaks a
plateau — while still being the template's most recent `SessionBest` if it is the latest local day
in the window. This is the exact shape D-07 describes: "last weight lifted" and "last
streak-qualifying weight" can differ, and this phase's field must report the former.

## STRIDE Threat Register

This phase is a backend-only, read-only analytics field addition: no new endpoint, no new MCP
tool, no new request parameter, no new database column or migration, no new external dependency,
and no change to authentication/authorization. The field is derived entirely from data
(`SessionBest.best_weight_kg`) already computed and already returned elsewhere in the same
response family (`ExerciseProgressionResult.points[].best_weight_kg`, exposed today via
`fitness_get_exercise_progression`). Every STRIDE category is assessed against that narrow change.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
