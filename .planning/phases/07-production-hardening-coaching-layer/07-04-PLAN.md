```bash
#!/usr/bin/env bash
# The single reproducible description of how BRETT's Hevy sync runs in production (D-10).
#
# `backend/app/cli.py` is the operations trigger; this is the scheduled production
# path blueprint 38 asks for (a sync every 1-6 hours). It is a Cloud Run JOB, not an
# in-process APScheduler: an in-process scheduler dies with a scaled-to-zero or
# restarted instance and leaves no run history, and the MCP service deploys with
# --min=0 by default.
#
# backend/tests/test_sync_job_deploy.py asserts every flag below is still here.
#
# PREREQUISITE, one-time (see docs and plan 07-07): the Secret Manager secret
# `brett-hevy-api-key` must exist and `brett-run@` must hold
# roles/secretmanager.secretAccessor on it. Only `brett-database-url` and
# `brett-mcp-auth-secret` existed as of the Phase 2 deploy.
set -euo pipefail

REPO_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"

# Never inherit `gcloud config get-value project`.
PROJECT_ID="${BRETT_GCP_PROJECT:?set BRETT_GCP_PROJECT}"
REGION="${BRETT_GCP_REGION:-us-central1}"
JOB="${BRETT_SYNC_JOB:-brett-sync-hevy}"
RUNTIME_SA="brett-run@${PROJECT_ID}.iam.gserviceaccount.com"

# One attempt plus one retry. A Hevy full sync is idempotent and resumable from its
# checkpoint (HEVY-08/09), so a retry is safe -- but a high retry count on a 6-hourly
# schedule can stack executions, and the next scheduled run is only hours away.
MAX_RETRIES="${BRETT_SYNC_MAX_RETRIES:-1}"
# Generous: /v1/workouts caps pageSize at 10, so a full historical sync is hundreds of
# sequential requests with tenacity backoff between failures.
TASK_TIMEOUT="${BRETT_SYNC_TASK_TIMEOUT:-1800s}"

exec gcloud run jobs deploy "$JOB" \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --source="$REPO_ROOT" \
  --service-account="$RUNTIME_SA" \
  --command=python \
  --args=-m,app.cli,sync-hevy \
  --tasks=1 \
  --max-retries="$MAX_RETRIES" \
  --task-timeout="$TASK_TIMEOUT" \
  --memory=512Mi \
  --env-vars-file="$REPO_ROOT/deploy/sync-job.env.yaml" \
  --set-secrets="DATABASE_URL=brett-database-url:latest,HEVY_API_KEY=brett-hevy-api-key:latest" \
  --set-build-env-vars="UV_FROZEN=1,UV_NO_DEV=1" \
  --quiet
```

public egress). Do NOT bind `MCP_AUTH_SECRET` — the CLI never constructs a token verifier.

**Create `scripts/create-sync-schedule.sh`** (mode 0755). A Cloud Scheduler HTTP job that calls
the Run Admin API's `:run` endpoint with an OAuth token — the documented way to trigger a Cloud
Run Job on a schedule:

```bash
#!/usr/bin/env bash
# One-time creation of the Cloud Scheduler trigger for the Hevy sync job (D-10).
#
# Separate from scripts/deploy-sync-job.sh on purpose: the job is redeployed on every
# code change, the schedule is created once. Re-running this script updates the
# existing schedule rather than failing, so it is safe to run again.
#
# Blueprint 38 wants a sync every 1-6 hours. Six hours, on the hour, in the user's own
# timezone: the analytics layer buckets by local Monday-start weeks in Asia/Jakarta, so
# a UTC-scheduled sync would land at four arbitrary local times and make "when was this
# last synced" harder to reason about than it needs to be.
#
# PREREQUISITE, one-time: `brett-run@` must hold roles/run.invoker on the job, and the
# cloudscheduler.googleapis.com API must be enabled (plan 07-07 does both).
set -euo pipefail

PROJECT_ID="${BRETT_GCP_PROJECT:?set BRETT_GCP_PROJECT}"
REGION="${BRETT_GCP_REGION:-us-central1}"
JOB="${BRETT_SYNC_JOB:-brett-sync-hevy}"
SCHEDULE_NAME="${BRETT_SYNC_SCHEDULE:-brett-sync-hevy-6h}"
SCHEDULE="${BRETT_SYNC_CRON:-0 */6 * * *}"
TIME_ZONE="${BRETT_SYNC_TZ:-Asia/Jakarta}"
RUNTIME_SA="brett-run@${PROJECT_ID}.iam.gserviceaccount.com"

RUN_URI="https://${REGION}-run.googleapis.com/apis/run.googleapis.com/v1/namespaces/${PROJECT_ID}/jobs/${JOB}:run"

# create-or-update: `describe` decides which verb to use, so a re-run is not an error.
if gcloud scheduler jobs describe "$SCHEDULE_NAME" \
     --project="$PROJECT_ID" --location="$REGION" >/dev/null 2>&1; then
  VERB=update
else
  VERB=create
fi

exec gcloud scheduler jobs "$VERB" http "$SCHEDULE_NAME" \
  --project="$PROJECT_ID" \
  --location="$REGION" \
  --schedule="$SCHEDULE" \
  --time-zone="$TIME_ZONE" \
  --uri="$RUN_URI" \
  --http-method=POST \
  --oauth-service-account-email="$RUNTIME_SA" \
  --attempt-deadline=60s \
  --quiet
```

`--attempt-deadline=60s` is deliberate and must be commented in the script: the deadline bounds
the `:run` API call that *starts* the execution, not the sync itself — the job's own
`--task-timeout=1800s` bounds the work.
