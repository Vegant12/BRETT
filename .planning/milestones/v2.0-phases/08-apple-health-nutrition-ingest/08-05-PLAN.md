<objective>
Turn a validated Health Auto Export payload into the exact set of day-grained rows the database
will hold: registry lookup, unit conversion, Hevy-source exclusion, local-day resolution, and
whole-payload aggregation.

Purpose: this is the phase's genuine novelty and where its two sharpest risks live.

**HEALTH-08 is not satisfied by a metric allowlist.** RESEARCH Finding A measured Hevy writing

body-mass and workouts routes; nobody checked active energy, because nobody knew Hevy wrote it.
Without a source-level exclusion predicate here, BRETT would double-count training energy it
already holds at set-level detail.

**Aggregation and idempotency are coupled** (Pitfall N-2). Real payloads carry 189 datapoints for
one metric-day; the table holds one row. Aggregating the *whole payload* before any write is what
makes plan 08-06's replace-semantics upsert correct.

Output: `normalize.py` and its unit test file. No database access — this module is pure.
</objective>

**Open Question 1 — the Hevy exclusion happens at WRITE time, not read time.** A Hevy-sourced
datapoint never becomes a row. This makes ROADMAP success criterion #4 ("volume, frequency and
body-weight numbers identical before and after Apple Health data exists") provable by a row-count
assertion instead of by auditing every future analytics reader — which is exactly the trap
`PITFALLS.md` Pitfall 9 describes for `_dedupe_by_day`. It also matches D-02's stated preference
for exclusion over quarantine. Cost, accepted and recorded: the evidence is discarded, and
recovering it would need a Phase 9 re-run.

**Open Question 2 — a data kind is "present" only when the payload carried >= 1 ACCEPTED metric of
that kind.** `kinds_present` drives which of D-03's two `sync_state` resources plan 08-06 advances.
Advancing both on every delivery would report nutrition "fresh" while the logging app has stopped
writing to HealthKit — precisely the blind spot D-03 exists to remove.

**Pitfall N-4 — `local_day` wins over the payload's own date part.** A nutrition app writing a
daily total anchors it at local midnight (`"2025-08-15 00:00:00 +0900"`). Read in `Asia/Jakarta`
(+07:00) that instant is `2025-08-14 22:00`, i.e. day **2025-08-14**. Keep `local_day` for
consistency with every other table in this project, and pin the known behaviour with a test rather
than leaving it to be discovered. Today the user is `Asia/Jakarta` and the phone emits `+0700`, so
this is dormant; it activates on travel or a mis-set `users.timezone`.

```python
def normalize_payload(payload: HAEPayload, *, tz: str) -> NormalizeResult:
    """Collect the WHOLE payload into day-grained rows before anything is written.

    Separating the read from the write is what makes idempotency a property of the type rather
    than a discipline the caller has to remember (`hevy/events.py::drain_events` is the same
    idea). Real payloads carry 189 datapoints for one metric-day and the table holds one row, so
    aggregation is mandatory -- and its interaction with the upsert's conflict clause is the
    sharpest correctness risk in this phase (Pitfall N-2):

        SET qty = qty + excluded.qty  -> correct across batches, DOUBLE-COUNTS a re-sent window
        SET qty = excluded.qty        -> correct on a re-send, LOSES the first of two batches

    This function resolves the first half: within one delivery, every datapoint for a key is
    summed once, here, so plan 08-06 can use replace semantics unconditionally. The second half
    -- a day split across two batched POSTs -- is resolved at the DEVICE, by requiring Health Auto
    Export's aggregation interval to be daily (see docs/health-auto-export-setup.md), and is made
    OBSERVABLE by the `health_ingest_multi_point_day` warning below. Under a correct device
    configuration that warning never fires; when it does, replace semantics has become lossy and
    the device setting has drifted.
    """
```
