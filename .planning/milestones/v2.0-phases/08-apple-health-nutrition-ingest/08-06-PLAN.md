<objective>
Persist a normalized payload idempotently and advance exactly the freshness resources the payload
actually carried.

Purpose: HEALTH-09 and NUTR-03 turn on one line — the conflict clause — and RESEARCH Pitfall N-2
shows both obvious choices are wrong in one direction:

| conflict clause | re-sending an overlapping window | a day split across two batched POSTs |
|---|---|---|
| `SET value = value + excluded.value` | **double-counts** — fails success criterion #3 | correct |
| `SET value = excluded.value` | correct, a no-op | **silently loses the first batch** |

Plan 08-05 already resolved the within-payload half by aggregating everything before the first
write. This plan takes **replace** semantics unconditionally, and the remaining risk — a batch
boundary falling inside a day — is closed at the device (daily aggregation interval, documented as
a deploy prerequisite in plan 08-08) and made observable by the `health_ingest_multi_point_day`
warning plan 08-05 already emits.

The second half of this plan is D-03: advance `('apple_health','activity')` and
`('apple_health','nutrition')` **independently**, each only when the payload contained at least one
accepted metric of that kind. Advancing both on every delivery would report nutrition "fresh" while
the logging app has stopped writing to HealthKit — the exact blind spot D-03 exists to remove.

Output: `ingest.py` and its integration test file. This plan does not create the HTTP route —
plan 08-07 does.

**`upsert_health_metric`:**

```python
async def upsert_health_metric(
    session: AsyncSession, *, user_id: uuid.UUID, row: NormalizedRow
) -> None:
    """Write one row, keyed on `(user_id, source, metric, source_name, local_day)`.

    Does not commit: the caller owns the transaction, so the payload's rows and the two D-03
    freshness timestamps land together or not at all.

    `user_id` is keyword-only with no default (ASVS V4): the schema is multi-user-ready, so an
    unscoped write is a cross-tenant defect a single-user suite cannot see. It is resolved
    server-side by the route and is NEVER read from the payload -- Health Auto Export cannot
    supply one and must not be able to.
    """
    stmt = pg_insert(HealthDailyMetric).values(
        id=uuid.uuid4(),
        user_id=user_id,
        source=SOURCE_APPLE_HEALTH,
        metric=row.metric,
        source_name=row.source_name,
        local_day=row.local_day,
        value=row.value,
        units=row.units,
        sample_count=row.sample_count,
    )
    # REPLACE semantics, never additive (HEALTH-09 / NUTR-03, RESEARCH Pitfall N-2). Plan 08-05
    # aggregates the WHOLE payload before the first write, so `excluded.value` is already the
    # complete total for this (metric, source_name, day) within this delivery -- adding it to the
    # stored value would double-count every re-sent window, which is precisely what ROADMAP
    # success criterion #3 forbids.
    #
    # `sample_count` is written on conflict too, deliberately: a sample_count that FALLS on a
    # re-sync is the cheapest available detector for a batch-split data loss, and it only works
    # if the column tracks the latest delivery.
    #
    # Bound to the constraint BY NAME rather than by column list, mirroring
    # `app.db.repositories.sync_state`: if the constraint is ever renamed this raises immediately
    # instead of silently degrading into a duplicate-row insert.
    stmt = stmt.on_conflict_do_update(
        constraint=_CONFLICT_CONSTRAINT,
        set_={
            "value": stmt.excluded.value,
            "units": stmt.excluded.units,
            "sample_count": stmt.excluded.sample_count,
        },
    )
    await session.execute(stmt)
```

**`ingest_payload`:**

```python
async def ingest_payload(
    sessionmaker: async_sessionmaker[AsyncSession], *, user_id: uuid.UUID, payload: HAEPayload
) -> HealthIngestResult:
```

1. Open a session; `tz = await _user_timezone(session, user_id=user_id)`.
2. `result = normalize_payload(payload, tz=tz)` — pure, no I/O, outside any write.
3. Loop `result.rows`, each inside `async with session.begin_nested():`, calling
   `upsert_health_metric`. On `SQLAlchemyError as exc`: increment `rows_skipped` and
   `log.warning("health_ingest_row_skipped", metric=row.metric, local_day=row.local_day.isoformat(), source_name=row.source_name, reason=type(exc).__name__)`.
   Class name only — `str(DataError)` renders the bound parameters, which here are this person's
   calorie counts.
4. `now = utc_now()`; for each `kind in sorted(result.kinds_present)`:
   `resource = _KIND_TO_RESOURCE[kind]`, then `ensure_sync_state(...)` and
   `complete_sync(session, user_id=user_id, provider=PROVIDER_APPLE_HEALTH, resource=resource, last_synced_at=now)`.
   Do **not** pass `cursor_timestamp` or `cursor_page` — a webhook has no resume point, and
   passing `cursor_timestamp=None` would reset a cursor that does not exist here anyway.
5. `await session.commit()`.
6. On `SQLAlchemyError` escaping the whole batch: open a **fresh** session (the first is
   poisoned), `record_sync_error` for each kind in `result.kinds_present`, commit, and re-raise.
7. `log.info("health_ingest_completed", rows_upserted=…, rows_skipped=…, datapoints_seen=…, metrics_unrecognized=…, kinds=sorted(result.kinds_present))`
   and return the `HealthIngestResult`.

Deliberate deviations from `hevy/body.py`, each worth a comment: no `mark_running` (a webhook has
no long-running phase to observe — the row goes straight to `idle` with a fresh `last_synced_at`),
no pagination, no client, no `advance_cursor_page`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Normalized rows → PostgreSQL | Payload-derived strings become bound parameters. Also where a wrong conflict clause silently corrupts history. |
| Ingest transaction → `sync_state` freshness claims | A timestamp written outside the rows' transaction would assert data exists that rolled back. |
| Caller-supplied `user_id` → row ownership | The only place a tenant is chosen for a write in this phase. |
| DB exception text → log sink / `sync_state.last_error` | `str(DataError)` renders bound parameters, which here are calorie counts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-34 | Tampering | additive conflict clause double-counting a re-sent window | mitigate | `set_={"value": stmt.excluded.value, ...}` — replace, never `value + excluded.value`. Proven by `test_identical_payload_twice_changes_nothing` against a real PostgreSQL constraint, and by an acceptance grep that fails on any `+` in the conflict clause. |
| T-08-35 | Tampering | conflict bound by column list rather than by name | mitigate | `on_conflict_do_update(constraint=_CONFLICT_CONSTRAINT)`. A renamed constraint then raises immediately instead of silently degrading into duplicate-row inserts — the same rule `sync_state` and `hevy/body.py` already follow. |
| T-08-36 | Repudiation | a freshness timestamp claiming work that rolled back | mitigate | `ensure_sync_state` + `complete_sync` execute in the SAME transaction as the rows and commit with them. `complete_sync`'s own guard rejects a naive `last_synced_at`, so `utc_now()` is passed explicitly. |
| T-08-37 | Spoofing | nutrition reported fresh when the logging app stopped | mitigate | Only kinds in `kinds_present` advance, and `kinds_present` counts accepted rows, not deliveries (Open Question 2). `test_activity_only_payload_does_not_freshen_nutrition` is the regression guard. |
| T-08-38 | Elevation of Privilege | payload-supplied tenant | mitigate | `user_id` is keyword-only with no default and is resolved server-side by the route from `DEFAULT_USER_ID` (ASVS V4). Health Auto Export cannot supply one; nothing in this module reads a tenant from the payload. Acceptance grep asserts no default. |
| T-08-39 | Information Disclosure | `str(exc)` writing calorie counts into `last_error` and logs | mitigate | Every skip path logs `reason=type(exc).__name__` only, and `record_sync_error` goes through `format_sync_error`, whose whole job is bounding that leak. | T-08-40 | Denial of Service | one bad row aborting the whole transaction | mitigate | `session.begin_nested()` SAVEPOINT per row. Without it, one `DataError` aborts the transaction and every later statement fails with "current transaction is aborted" — losing the whole window for one bad datapoint, on an endpoint whose sender never retries. |
| T-08-41 | Tampering | SQL injection via `source_name` / `metric` | mitigate | Values are bound parameters through SQLAlchemy Core `pg_insert(...).values(...)`; no string is interpolated into SQL anywhere in this module. Column widths bound the stored length. |
