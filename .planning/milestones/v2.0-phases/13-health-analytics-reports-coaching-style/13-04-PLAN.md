<objective>
Build `app/analytics/health.py` — the activity and nutrition trend arithmetic HEALTH-12 and
NUTR-04 ask for — and the schemas it returns.

Purpose: this is the only genuinely new arithmetic in Phase 13. D-05 and D-06 lock its shape to
`bodyweight.py`'s rolling-average / independent-per-window-floor design and explicitly reject
`body_measurements.py`'s latest-vs-90-days design, because activity data arrives daily from the

its own averaging — which ARCHITECTURE.md Anti-Pattern #9 and D-02/D-03 forbid — it exposes a
second entry point per data kind taking an explicit period: the same fold, a different window.

**C. Six models**, all subclassing `_AnalyticsModel`.

`MetricWindowAverage`: fields `window_days: int`, `average: Decimal | None`,
`total: Decimal | None`, `coverage: MeasurementCoverage`.
Docstring: `average` and `total` are BOTH `None` when `coverage.insufficient_data` is True — the
arithmetic exists either way, but a 30-day step average built from two logged days presents a
fiction as a trend, which is `BodyWeightTrendResult`'s rule exactly. `total` sums the MEASURED
days only, never the window length: there is no interpolation and no carry-forward, for
`bodyweight.py` D-13's reason, so `total` answers "how much did you log across the days you
logged" and never "how much did you do this week" — a distinction that matters most for
nutrition, where a missed logging day is not a fasted day.

`MetricTrend`: fields `metric: str`, `unit: str`, `windows: list[MetricWindowAverage]`,
`change_percent_7d_vs_30d: Decimal | None`, `latest_measured_on: dt.date | None`,
`latest_value: Decimal | None`.
Docstring: `windows` holds exactly three entries in ascending `window_days` order (7, 14, 30) —
a list rather than three named fields because every consumer iterates them and because the
per-window independence is the point (D-15: a 30-day average can be trustworthy while the 7-day
one is not). `change_percent_7d_vs_30d` is HEALTH-12's "rate of change" and is deliberately NOT
`bodyweight.py`'s four-week smoothed anchor: that anchor exists to strip water and glycogen
noise from a slow signal whose raw weekly delta is nearly three times the threshold it is
compared against, whereas activity and intake are fast, high-variance, daily-measured signals
whose real question is "has my activity dropped off lately" — this week against the last month.
It is `None` when EITHER window fails its own floor, because a ratio with one trustworthy
endpoint and one guess is not half-trustworthy, it is wrong. `latest_measured_on`/`latest_value`
are populated independently of every floor: one real observation is worth surfacing, and
suppressing it would report "no data" for a metric the user demonstrably recorded.

**`period_measured_day_floor(days_in_period: int) -> int`** — a PURE function:

    if days_in_period < 1:
        raise ValueError("period length must be at least one day")
    scaled = int(
        (Decimal(days_in_period) * PERIOD_FLOOR_FRACTION).to_integral_value(rounding=ROUND_CEILING)
    )
    return min(max(PERIOD_FLOOR_MIN_DAYS, scaled), days_in_period)

Docstring must state the load-bearing property: this GENERALIZES `MEASURED_DAY_FLOORS` rather
than competing with it. `ceil(0.33 * n)` reproduces D-15's three published floors exactly —
7→3, 14→5, 30→10 — which is what makes a computed floor for an arbitrary report period
defensible instead of invented. The `min(..., days_in_period)` clamp exists because a 1-day
period cannot satisfy a floor of 2 and would otherwise report `insufficient_data` for a period
whose only day was fully logged. `is_measurement_insufficient` is deliberately NOT reused here:
it raises on an unsupported window length by design, and relaxing that to serve this path would
weaken the guard for `bodyweight.py` too.
