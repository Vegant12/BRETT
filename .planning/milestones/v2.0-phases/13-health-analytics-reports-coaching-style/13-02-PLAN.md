
Body: `insert(HealthDailyMetric).values(id=uuid.uuid4(), user_id=user_id, source=source,
metric=metric, source_name=source_name, local_day=local_day, value=value, unit=..., 
sample_count=sample_count)` followed by `await self._session.flush()` — the exact
flush-not-commit contract every other builder method has.

`unit` defaults to `None` and, when `None`, is resolved as
`METRIC_REGISTRY[metric].canonical_unit`. Import `METRIC_REGISTRY` from
`app.integrations.health_auto_export.registry` — `conftest.py` is a TEST module, so
`test_analytics_isolation.py`'s "analytics must not import app.integrations" guard does not
apply to it, and resolving the unit from the registry is what stops a fixture from seeding
`kJ` where production stores `kcal`. An unknown `metric` therefore raises `KeyError` at seed
time, which is correct: a typo'd metric name would otherwise seed a row no analytics query can
ever find, and the test would pass by returning an honest empty result for the wrong reason.

`source_name` is a PARAMETER with an `'iPhone'` default, not a constant, for exactly the reason
`body_measurement.source` is one: the multi-source-per-day case is real production data
(`docs/health-auto-export-setup.md`, 2026-08-23: `Foodvisor` and `Built With Science` both wrote
`DietaryEnergyConsumed`), and the analytics fold must be provably summing across `source_name`
rather than picking one row.

`value` is `Decimal`, never `float` — these average into rolling 7/14/30-day figures and binary
floating point would make two arithmetically identical averages compare unequal. Write the
docstring saying so, matching `body_measurement`'s.
