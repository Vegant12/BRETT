Content, in the document's existing plain, second-person voice:

- Phase 9's one-time backfill imports `export.xml` and writes `sample_count` = the number of **raw
  HealthKit samples** aggregated into that day. Raw samples are per-event, not per-day: measured on
  the real export, **7,403 of 8,077 backfilled rows (91.7%)** aggregate more than one sample.
- The webhook writes `sample_count = 1`, because Aggregate Data makes the phone send one datapoint
  per metric per day (confirmed live 2026-09-03).
- `health_daily_metrics.sample_count` is documented as "the cheapest diagnostic for Pitfall N-2" —
  a `sample_count` that **falls** on a re-sync is a batch-split data loss. On a day that the
  backfill covered and the webhook later re-delivers, `sample_count` legitimately drops from N to
  1. That is a **false positive**, and it is expected exactly once per overlapping day.
- How to tell the two apart: the false positive lands on days **on or before the backfill's
  `ExportDate`** and coincides with the value being replaced by a correct daily total. A real
  batch-split loss lands on a **recent** day and coincides with the day's total getting smaller.
- Why this is accepted rather than fixed: `sample_count` is diagnostic-only, feeds no analytics,
  and the alternative — making the backfill write `sample_count = 1` — would be the backfill lying
  about what it aggregated, which is worse. Record it here so it does not cost a future debugging
  session.
- One line noting that in practice the overlap is expected to be **zero days**: the export ends
  2026-08-26 and the live webhook feed starts 2026-09-02. Verify empirically with the `--dry-run`
  summary's date range before the real run rather than assuming it.
