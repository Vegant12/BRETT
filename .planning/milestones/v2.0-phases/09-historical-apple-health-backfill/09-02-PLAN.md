- **"Why this reuses `normalize_payload` literally"** — the CONTEXT non-negotiable is that the
  backfill and the webhook produce byte-identical rows for the same logical datapoint. Both shapes
  were measured against the real 191 MB file and produce identical output (8,077 rows, identical
  counters); the literal-`HAEPayload` variant costs 311 MB peak instead of 67 MB and buys

  unit conversion, Hevy exclusion, day bucketing and aggregation — five places to diverge.
- **"The two-clear memory discipline"** — `elem.clear()` alone leaves the emptied element attached
  to the root, so `HealthData` accumulates 438,649 empty `Element`s. Measured on the real file:
  both clears 16.2 MB, `elem.clear()` only 53.5 MB, no clear 385.2 MB. Stdlib `Element` has no
  `getparent()`; capturing the root from the first `start` event and calling `root.clear()` is the
  workaround, and it is safe here because every `Record` is a direct child of `HealthData` and is
  fully consumed at its `end` event.
- **"Never key on `type=` alone"** — `<WorkoutStatistics type="HKQuantityTypeIdentifierActiveEnergyBurned"
  sum="228" unit="kcal"/>` is a child of `<Workout>` (224 of them in the real file). It carries the
  same `type=` string as a real `Record`, uses `sum=` not `value=`, and has no `sourceName`, so
  `is_hevy_sourced(None)` returns `False` by design and would let Hevy's own workout energy in
  through the back door. Branch on `elem.tag == "Record"` first, always.
- **"Whole file, then write"** — positional chunking of the parse would be a data-loss bug:
  `export.xml` is grouped by record type and only then chronologically, so one local day's records
  are scattered across the whole file, and replace semantics silently drops the earlier half of a
  split day. It is also the reason a multi-row `ON CONFLICT DO UPDATE` cannot raise
  `CardinalityViolationError` here — `normalize_payload` returns rows keyed by a dict, so duplicate
  conflict keys are structurally impossible.
- **"The logging rule"** — copy `ingest.py`'s wording: a metric name, a HealthKit type identifier,
  a `local_day`, a `source_name`, a count and an exception class name are loggable; a measured
  quantity is not, ever, and neither is a raw attribute value from the file.
- **"XML trust"** — the threat-model justification for the `noqa` (see below).

**(a) The multi-point-day warning filter (Pitfall 4).** On the real file `normalize_payload` emits
`health_ingest_multi_point_day` **7,403 times** — 91.7% of rows aggregate more than one raw sample,
which is completely normal for raw HealthKit data and inverts the warning's documented meaning
("under a correct device configuration that warning never fires"). 7,403 lines would bury the

of the backfill's `normalize_payload` call only — **never change `normalize.py`'s behaviour for the

Implement as a stdlib `logging.Filter` attached to the root logger's **handlers** (not to the
logger), because `configure_logging` installs one root `StreamHandler` and a handler-level filter
sees propagated records while a logger-level one does not. With
`ProcessorFormatter.wrap_for_formatter`, `record.msg` is the structlog event dict:

```python
class _MultiPointDayCounter(logging.Filter):
    """Swallow `health_ingest_multi_point_day` and count it instead (Pitfall 4).

    For the WEBHOOK that warning means the device's daily aggregation has drifted and replace
    semantics has become lossy. For the BACKFILL it means raw HealthKit samples are per-event,
    which they always are -- 7,403 of 8,077 rows on the real file. Attached to the root
    HANDLERS rather than to a logger: a logger-level filter does not see propagated records,
    and every module in this package logs through its own `structlog.get_logger()`.
    """

    def __init__(self) -> None:
        super().__init__()
        self.count = 0

    def filter(self, record: logging.LogRecord) -> bool:
        event = record.msg.get("event") if isinstance(record.msg, dict) else None
        if event == "health_ingest_multi_point_day":
            self.count += 1
            return False
        return True
```

and a `contextlib.contextmanager` `_suppressing_multi_point_days()` that yields the counter,
adding it to every handler on `logging.getLogger()` on entry and removing it from every one of them
in a `finally`. Handle the zero-handler case (a process that never called `configure_logging`)
without raising.

**(b) `scan_export`.** Signature:

```python
def scan_export(path: Path, *, tz: str) -> BackfillScan:
```

Pure, synchronous, no database, no I/O beyond reading `path`. Body:

1. Open the stream:
   ```python
   try:
       it = ET.iterparse(path, events=("start", "end"))
       _, root = next(it)
   except (OSError, ET.ParseError, StopIteration) as exc:
       log.error("health_backfill_unreadable", reason=type(exc).__name__)
       raise HAEExportFileError from None
   if root.tag != "HealthData":
       raise HAEExportFileError
   ```
   `from None` throughout, for the reason `parse_hae_datetime` gives: chaining re-attaches the
   exception whose message is the problem — here, a parse error rendering a byte offset into the
   user's entire health history.

2. Buckets keyed by `(wire_metric, unit_string)`:
   ```python
   buckets: dict[tuple[str, str], list[dict[str, object]]] = defaultdict(list)
   ```
   Keying on the unit as well as the name is deliberate and costs nothing: HAE units are a
   per-metric user preference that changes silently on the next export, and one `HAEMetric` carries
   exactly one metric-level `units`. Two entries with the same `name` and different `units` both
   convert correctly through `to_canonical` and land in the same `normalize_payload` bucket, so a
   mid-file unit change is handled with zero extra logic instead of being silently mis-converted.

3. The loop, exactly this shape:
   ```python
   for event, elem in it:
       if event != "end":
           continue
       tag = elem.tag
       if tag == _RECORD_TAG:
           ...  # (4) below
       elif tag in _SKIP_AND_COUNT:
   ```
