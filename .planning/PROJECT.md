# BRETT

## What This Is

A personal fitness data platform that normalizes Hevy workout data, Apple Health data, body-composition measurements, and nutrition data into PostgreSQL, calculates fitness analytics (volume, progression, plateaus, PRs, trends), and exposes it through a remote MCP server so Claude can act as a long-term, data-driven body recomposition coach. v1.0 (shipped) was backend-first: Hevy sync, analytics, and a read-only remote MCP server. v2.0 adds Apple Health data (via a Health Auto Export webhook, not a native app), max-weight-lifted surfaced as a display-only complement to the existing estimated-1RM strength signal, scheduled report tools, richer body-measurement history, and switchable training programs — with one narrow, confirm-gated MCP write tool as the sole exception to read-only.

## Core Value

Claude can retrieve real, normalized workout data through the MCP server and answer training questions ("Am I progressing?", "Which muscles are undertrained?") from actual data instead of guessing. This end-to-end path — Hevy → PostgreSQL → analytics → MCP → Claude — must work before anything else matters.

## Current Milestone: v2.0 Apple Health, Strength Tracking & Coaching Programs

**Goal:** Extend BRETT beyond Hevy-only into a full recomposition coach — ingesting Apple Health activity and nutrition data, surfacing the last weight actually lifted alongside the existing estimated-1RM strength signal, remembering physical progress over time, adapting to the active program, and answering with concise, report-ready summaries Claude can deliver on a schedule.

**Target features:**
- Apple Health integration via a Health Auto Export webhook receiver, no native app or Apple Developer Program needed — with a hard exclusion filter for Apple Health workouts/body-mass rows that are actually Hevy re-exports
- One-time historical Apple Health backfill from `export.xml`, same exclusion filter
- Health analytics extension, activity only (steps/energy/distance/flights) — sleep/recovery cut for lack of any real data (no Apple Watch)
- Nutrition data (calories + six consistently-logged macros) via the same Apple Health pipeline — the user already logs nutrition into an app that writes to HealthKit, so no dedicated provider integration is needed; supersedes the old deferred "automatic nutrition provider" item
- Strength tracking: last max-weight-lifted surfaced as a labelled display-only field on progression/plateau responses; estimated-1RM keeps classifying trend and plateau verdicts, unchanged
- Weekly/monthly report MCP tools, valuable on-demand; Claude scheduled-task delivery spiked early and verified, not assumed
- Concise, simple coaching response style
- Historical body measurements: trend/comparison analytics beyond weight-only, over data already synced from Hevy (no manual entry — dropped 2026-09-03, see Key Decisions)
- Training programs (Lean Bulk/Cut/Recomp) as real data, with a token-based confirm-gated MCP write tool to switch programs

### Out of Scope

- Self-hosted / hand-rolled OAuth authorization servers — WorkOS AuthKit *is* the authorization server; BRETT is only a resource server that validates its tokens. *(This replaces the original scope note, which deferred OAuth for MCP auth on the grounds that a bearer token was sufficient for private v1 development. That note was overturned in Phase 2: a Claude custom connector cannot authenticate with a static bearer at all, so OAuth 2.1 was implemented rather than deferred — see the "MCP connector auth" row in Key Decisions. What stays out of scope is building the authorization server ourselves.)*
- A native iOS HealthKit app — superseded for v2.0 by the Health Auto Export webhook approach (no Apple Developer Program needed); the blueprint's native `FitnessSync` app design remains a documented option if a native app is ever wanted later
- Manual nutrition entry, and nutrition data not already present in Apple Health — nutrition work in v2.0 is scoped to what a real Apple Health export already has (calories + six consistently-logged macros, via the existing Health Auto Export pipeline); a dedicated provider integration or manual entry beyond that was not requested
- Write/delete MCP tools beyond the one confirm-gated program-switch tool — MCP otherwise stays read-only; this is a narrow, deliberate exception, not a general opening of write access
- Multi-user product features (accounts for other people, per-user auth flows beyond schema readiness) — schema must not preclude multi-user later, but no multi-user UX is built now

## Constraints

- **Tech stack**: Python 3.12+, FastAPI, PostgreSQL, SQLAlchemy 2.x, Alembic, Pydantic, httpx, MCP Python SDK, pytest, Ruff (mypy where practical) — specified in the blueprint, not open for re-litigation without cause
- **Repo layout**: Flat at the BRETT repo root (`backend/`, `ios/`, `docs/` as top-level dirs) — no extra `fitness-platform/` nesting, since this repo already is the project root
- **Security**: MCP tools read-only in v1; from v2.0, exactly one narrow, confirm-gated write tool (program switching) is permitted as a deliberate exception, not a general opening of write access; never expose API keys, DB credentials, or internal tokens through MCP responses or logs; HTTPS everywhere; secrets only via environment/secret storage, never committed
- **Data integrity**: Hevy sync must be idempotent and must never corrupt existing data on partial/failed sync
- **Provider isolation**: Hevy-specific logic confined to `backend/app/integrations/hevy/` so the API surface can change or a new provider can be added without spreading assumptions through the app
- **Deployment**: Google Cloud Run for v1 (supersedes Render as of 2026-08-27, revised D-06), with external managed Postgres (Neon) and Google Secret Manager; architecture stays portable to another host later
